# Apple TV, Apple Watch and iPhone Duo

The simulator commands in [simulator input](simulator-input.md) also run on tvOS, watchOS and the foldable iPhone Duo; [the research](other-families-research.md) recorded what worked unchanged. One physical device of these families has been driven, [an Apple TV 4K](#a-physical-apple-tv); the watch and the Duo are simulators only. This page covers what was added for those families and what each addition was checked against. Evidence is in [verification](verification.md#other-simulator-families).

## Displays (iPhone Duo)

An iPhone Duo simulator has two integrated displays: the outer `LCD` (screen ID 1, device name `primary`, 466 × 678 points at 3×), which the simulator marks primary, and the inner `LCD-1` (screen ID 3, `primary-1`, 669 × 951 points). It also lists `TVOut`, `Wireless` (CarPlay) and `Resizable`, which have no framebuffer until something is connected. `simctl io screenshot` and `recordVideo` refuse to choose between the two integrated displays.

```sh
manzanero displays --simulator <UUID>                       # every display, with id, size, backlight, active, primary
manzanero screenshot tmp/outer.png --simulator <UUID>       # the display the interface is on
manzanero screenshot tmp/inner.png --simulator <UUID> --display LCD-1
manzanero screen ocr --simulator <UUID> --display 3
manzanero record tmp/inner.mp4 5 --simulator <UUID> --display primary-1
```

- `displays` reads the simulator's display information (the same read-only `dtdeviceinfod` request touch uses) and prints each display's `id`, `name`, `deviceName`, `type`, pixel and point size, `backlightState`, `active`, `currentOrientation`, `primary` and `capturable`, plus `defaultCaptureDisplay` and `interfaceDisplay`.
- **The interface display** is the display marked primary, except when that display is not awake and exactly one other integrated display with a framebuffer is `activeOn`: then it is that one. Only an unfolded iPhone Duo is in that case (the primary flag stays on the outer `LCD` while the interface is on `LCD-1`). With both integrated displays awake, which happens for a moment while folding and after a fresh boot, it is the primary one. A display without a framebuffer (`Resizable`) is never chosen, so a phone whose display is off is still refused as `display-off`.
- `screenshot`, `screen` and simulator `record` take `--display <name|device name|screen ID>`; names ignore case. Without it a simulator with one capturable display gets exactly the `simctl` invocation it got before, and a simulator with several gets `--display=<screen ID>` of the interface display. An unknown display, or one without a framebuffer, is refused with `ambiguous-or-missing-target` before anything is captured. Manzanero always passes the numeric screen ID to `simctl`.
- On a physical device `--display` is refused as `unsupported-operation` before any device contact; `displays` is simulator-only.
- `screen` reads the accessibility tree only for the interface display. With another display, `auto` describes the image by OCR and says why in `diagnostics`, and `tree` is refused before capture.
- Trees, waits, selector actions and touch follow the interface display. They take no display option. See [the inner display](#the-inner-display-unfolded) for what that changes on an unfolded Duo.

MCP: `list_displays`, and an optional `display` field on `screenshot`, `get_screen` and `record_screen`.

## Fold (iPhone Duo)

```sh
manzanero fold --simulator <UUID>          # hinge 0: outer display LCD
manzanero unfold --simulator <UUID>        # hinge 180: inner display LCD-1, landscape
manzanero hinge 110 --simulator <UUID>     # any angle 0...180, no display promised
manzanero hinge --simulator <UUID>         # read the angle (no input)
```

Each sends one `IndigoVendorDefinedEvent` to the simulator's `com.apple.coredevice.feature.remote.hid.vendordefined` service: usage page `0xFF61`, usage `0x5B`, version 0, and as data a binary `IOCFSerialize` of `{source: "hinge-slider-control", type: "range", value: <degrees>}`, the event Device Hub's hinge control sends ([research](duo-fold-research.md)). It goes through the same input path as buttons and keys: readiness barrier, the event (the service sends no reply), completion barrier and the input drain before the connection closes. The research lost the event when the connection closed at once; the drain keeps it open long enough. The simulator animates to the angle itself (0 to 180 in about 0.3 s).

- **`fold` and `unfold` wait for the display.** After sending 0 or 180 they read the display information every 250 ms, at most 40 times and 10 s, until the expected integrated display is `activeOn` and the other is `off`: the primary one (`LCD`) for `fold`, the other one (`LCD-1`) for `unfold`. The receipt has `expectedDisplay`, `activeDisplay` (the one integrated display awake at the last read, or null when none or both are), `displayObserved` and `displayReads`. When the display was not observed in time the command still exits 0 and says so in `note`; nothing is resent. That happened once in five folds on a Mac with three other simulators booted; with two others booted, five folds and five unfolds were all observed. It has not been tried with nothing else booted. On the iOS 27.2 runtime unfolding was observed after 3 reads and folding after 11 (about 2.7 s), with both displays reading awake in between.
- **`hinge <degrees>` promises no display.** Whether an intermediate angle swaps the display depends on how the hinge got there: 0 → 110 in one step unfolded, 0 → 45 → 70 → 110 in steps did not, and 180 → 90 stayed unfolded. So `hinge` reads the display information once right after sending and reports it with `displayObserved: false`.
- **Reading the angle.** `hinge` without an angle sends the CoreDevice action `com.apple.coredevice.action.streamhingeangle` to the simulator's `com.apple.coredevice.feature.monitormotion` service (in `dtdeviceinfod`), takes the first pushed sample, which is the current state, within 3 s, and cancels the connection, which ends the stream. It prints `angle`, `mechanicalAngle`, `minAngle` (0), `maxAngle` (180), `velocity` (degrees per second) and `isAngleValid`, with `activeDisplay` from the display information. `angle` and `mechanicalAngle` differ slightly at rest and depend on the direction: mechanical 90 read as 94.62 coming from 180 and as 85.38 coming from 0, mechanical 120 as 113.84, while 0 and 180 read exactly. It is an observation: no lease, no handoff pause, no input.
- **Posture, derived.** `hinge` (read) and `displays` on a foldable simulator also give `posture`: `closed` up to 5 degrees, `flat` from 175, `partially-open` between (`unknown` when the sample says the angle is invalid). Manzanero derives it from `angle` with these thresholds of its own; the simulator does not report it (the device-motion stream other tools read posture from was not found), and they are not Apple's `UIHinge` boundaries, which depend on velocity. `postureSource` says so in every result. `displays` adds a `hinge` object (`angle`, `isAngleValid`, `posture`, `postureSource`) only for foldable simulators, so other simulators send exactly the one request they sent before; a failed angle read appears as `hinge.error` and the displays are still listed.
- **Foldable only.** A simulator is foldable when its display information lists exactly two integrated displays with a framebuffer, one of them primary; no device-type key marks a foldable. Others are refused as `unsupported-operation` after that read-only request and before any input; a physical device is refused before any contact.
- **Cancellation.** SIGINT during the wait stops it (exit 130); the hinge connection has already closed, and each display read opens and closes its own. The event itself was sent, so the device may end up folded or unfolded.
- `fold`, `unfold` and `hinge <degrees>` take the simulator lease like other input, and hold the command service for their whole duration, wait included, so a second call to the same CLI or MCP server cannot run between the event and the display check.

MCP: `fold_device` (`state`: `fold` or `unfold`), `set_hinge_angle` (`degrees`) and `get_hinge_angle` (read-only).

### The inner display (unfolded)

Unfolded, `LCD-1` reports `nativeOrientation: rot0`, `currentOrientation: rot90`, 2007 × 2853 pixels at 3× (669 × 951 points), and the interface is landscape, 951 × 669 points; the device reports `landscapeRight`. What follows the interface display there, all measured on the iOS 27.2 runtime with the [probe app](probe-app.md) launched with `-ProbeAllowRotation YES` (its view reported 951 × 669):

- **Touch goes to LCD-1's own Universal HID touchscreen.** Indigo digitizer events (`hid.digitizer`) never reached `LCD-1`: a raw tap with the payload's `target` 0, 1, 2, 3, 4 or 5 left the probe at zero touches. The Universal HID service lists one touchscreen per display, `CoreDevice touchscreen(<uniqueId>)`, and the one named after `LCD-1`'s unique identifier delivers. So on a non-primary interface display, `tap`, `long-press`, `swipe`, `drag`, `pinch` and two-path `multi-drag` send their usual samples as Universal HID complete-state reports to that touchscreen (`route: universal-hid` and `frameCount` in the receipt; schedules longer than the bridge's 512 frames, such as a 10 s long press, are thinned evenly). `multi-tap`, `gesture` and three-to-five-path `multi-drag` already used Universal HID and now pick that display's touchscreen. Coordinates map as on a phone in landscape right: interface (x, y) is the touchscreen's (y, 1 − x).
- **Accessibility hit tests name the display.** Trees worked unchanged (the frontmost-application request answered), but every hit test failed with error 8 until it carried `LCD-1`'s screen ID: hit and frontmost requests now send `displayId` 3 instead of 0, with the point mapped to `LCD-1`'s native portrait points (interface (475.5, 563) is (563, 475.5)). Display 0, 1 or 2, or unmapped interface points, were refused. On the primary display the requests are unchanged (`displayId` 0).
- **Geometry.** Trees, waits and actions use the interface size 951 × 669 and `rot90`; the result's `screen` object gives `LCD-1`'s native size and adds a `display` object (`id`, `name`, `deviceName`, `primary: false`). On the primary display `screen` keeps its shape.
- **Captures** default to `LCD-1` (`--display=3`), so `screenshot`, `screen` and `record` without `--display` show the interface; `screen` reads the tree for it.

Observed working unfolded: `tree`, `press` (by label and by identifier), `scroll --id` (Settings' StandBy row, `postcondition-verified`), `wait`, `set-value`, `type` into a focused field, `tap` (landed at 0.2499, 0.7499 for 0.25, 0.75), `long-press` (held 1.502 s for 1.5), `swipe`, `drag`, `pinch`, two-path `multi-drag`, `multi-tap` with 3 and 5 contacts, `screen`, `screenshot` and `record`; folded, the same commands ran on `LCD` by the old route (Indigo for one and two contacts, no `route` key), and on an `iPhone 17e` the requests and the `simctl` invocation were unchanged.

Not working or not tried:

- The Home Screen tree fails unfolded as it does folded on this runtime; unrelated to the display. It is not the snapshot time budget that the depth-10 retry works around on other simulators: SpringBoard is the frontmost process, and its snapshot came back empty at depth 8, 6, 4 and 2 as well, and for elements hit-tested on an icon and in the dock. Only a hit on a widget answered, with the widget renderer's own small tree. `screen` falls back to OCR there.
- Right after `simctl launch` of Settings unfolded, the frontmost request still named the previous app for a few seconds while Settings drew a blank window; a later `tree` read Settings. In its two-column layout `press --label General` is refused as ambiguous (sidebar row and detail title, both visible); the failure now lists the matches, among them `identifier 'com.apple.settings.general'`, and `press --id com.apple.settings.general` worked.
- A portrait-only app is letterboxed on `LCD-1`: the probe app, launched without `-ProbeAllowRotation YES`, got a 469 × 669-point window centred on the 951 × 669 display. Its tree's frames are relative to that window, so `press` fails at the hit test ("semantic refusal or notification in request response (error 8)"), and normalized touch coordinates are the display's, not the window's: a contact outside the window does not reach the app. Launch an app that can rotate, or tap by display coordinates; mapping by the window's origin is not built ([record](verification.md#the-duos-inner-display)).
- The hit-test fallback for a simulator that reports no frontmost application was not run on `LCD-1`. Only `rot90` was seen; whether `LCD-1` turns to other orientations, and whether the mapping holds then, is unknown.

The [touch runner](probe-touch-runner.md)'s built-in plan later ran once on `LCD-1`, with `gesture` and a three-path `multi-drag` among its 14 actions: all 14 and 29 of 29 contacts were delivered, one to five at once ([record](verification.md#the-duos-inner-display)). Four- and five-path `multi-drag` ran afterwards, and every contact inside the app's window arrived.

## Siri Remote (Apple TV)

```sh
manzanero remote <select|menu|home|play-pause|up|down|left|right> --simulator <UUID>
manzanero remote home --hold 1.5 --simulator <UUID>     # a long press: Control Centre
manzanero remote swipe-down --simulator <UUID>          # one finger across the touch surface
```

| Button | Sent | Observed effect (tvOS 27.2 simulator) |
| --- | --- | --- |
| `up`, `down`, `left`, `right` | Keyboard usage 82, 81, 80, 79 on `hid.keyboard` (as `key up` …) | Focus moved between Settings rows and between the probe's buttons; SwiftUI's `onMoveCommand` received each direction |
| `select` | Keyboard usage 40 (Return) | Opened the focused Settings row; triggered the focused SwiftUI button |
| `menu` | Consumer usage 0x46 (Menu Escape) on `hid.button` | Settings went back one level; SwiftUI's `onExitCommand` fired |
| `home` | Consumer usage 0x40 (as `button home`) | Went to the Home Screen |
| `play-pause` | Consumer usage 0xCD | SwiftUI's `onPlayPauseCommand` fired once per press |

Buttons are held 80 ms, like the phone's. `--hold <seconds>` (0.08...3; MCP `hold_seconds`) holds any of the eight longer: `remote home --hold 1.5` opened Control Centre on the tvOS 27.2 simulator, with Power Off, Audio, Do Not Disturb and Sleep Timer read off the screen, and `remote menu` closed it. `select` and the arrows are keys, held as one key down and one key up that far apart. On the simulator, against the [tvOS probe](probe-app.md#tvos-probe) on 2026-11-18: `remote select --hold 1.5` and `--hold 1.2` on the probe's Hold element were each recorded as `select-long`, and a plain `select` and `--hold 0.5` were not; `remote down --hold 2` repeated, and moved focus from row 1 of the probe's list to row 18. Control Centre is not in the tree (the frontmost application is `PineBoard`, 24 nodes, none of them an item), so read it with `screen ocr` and move in it with the arrows; it closes by itself after about half a minute.

On a physical Apple TV, since 2026-11-19, the keys can be held and `home` cannot ([record](verification.md#held-remote-buttons-on-the-apple-tv-4k)). `remote select --hold 1.5` and `--hold 1.2` on the probe's Hold element were recorded as `select-long` on the Apple TV 4K, and a plain `select` between them was not; `remote down --hold 1.5` repeated, from the first row of the probe's list to row 14. Menu and Play/Pause are keys on a device, so they hold the same way: `remote menu --hold 1` left the probe for the Home Screen, which is what holding Back does on tvOS, so the probe recorded nothing. `remote home --hold` is refused before any contact: Home is the one button on the device's button service, and a 1.5 s hold there ended with the connection failing during the hold ("Input stopped after cancellation or transport failure"), with neither Control Centre nor the Home Screen appearing, and input quarantined until cleared. Control Centre is therefore not reachable on a device through this tool. Apple's Device Hub does not reach it either: read from the Mac's log, it uses the same button service and sends the press and the release of Home within a millisecond, however long its button is held.

**Power Off on a simulator puts it to sleep, and nothing sent to it wakes it.** `remote home --hold 1.5`, `remote down` (focus moves to Power Off) and `remote select` made PineBoard log `Sleep:UserSystemMenu`; the simulator stayed `Booted` and its screenshot was black. Asleep, the tree's frontmost application is `PineBoard` with a `PBHotBlackWindow` node, which an awake tree does not have: that node is the sign of sleep, because `displays` reports the simulator's external display as inactive with its backlight off both awake and asleep. Then every `remote` button, `remote home --hold 1.5`, `button lock`, `button home` and `key space` were dispatched and changed nothing: `backboardd` logged the Home press with `destinations:<none>`, so no process was listening for buttons. `launch` was refused by the system ("System is asleeping - foreground app launch forbidden"). A `remote swipe-down` and a raw System Wake Up button event (usage page 1, usage 0x83) changed nothing either; `backboardd` logged the swipe's pointer events with `destinations: ()`. `shutdown` then `boot` brought it back, each of the four times. What a real Apple TV does may differ; [what wakes the device](#a-physical-apple-tv) is still unknown. A hold is refused on a physical Apple TV, where it has not been tried; `button lock` opens Control Centre there. `remote` takes the simulator lease, sends no touch and is refused as `unsupported-operation` before any input on a simulator whose CoreSimulator product family is not Apple TV. The product family comes from the simulator's device type. With `--device` it drives [a physical Apple TV](#a-physical-apple-tv).

Apple TV has no touch screen: `tap`, `long-press`, `swipe`, `drag`, `pinch`, `multi-tap`, `multi-drag` and `gesture` on an Apple TV simulator are refused as `unsupported-operation` with a pointer to `remote`, before the display is read. Swipes on the remote's touch surface are [`remote swipe-…`](#remote-touch-surface). `key`, `type`, `button home`, trees, waits and `press` work as on a phone.

MCP: `press_remote` (`platform`: `simulator`, the default, or `physical`).

### A physical Apple TV

Run on one Apple TV 4K (3rd generation, tvOS 27.2) on 2026-11-18 ([record](verification.md#first-look-at-a-physical-apple-tv)). Nothing here is known for another model or tvOS version.

**Any command may switch it on.** A first pass of commands that only observe (`readiness`, `apps`, `media-status`, `screenshot`) switched a sleeping Apple TV on, and the television connected to it. Which command did it is not known. Tell whoever is in the room first.

```sh
manzanero remote <select|menu|home|play-pause|up|down|left|right> --device <UDID>
manzanero tree --device <UDID>
manzanero wait --label Settings --until focused --device <UDID>
manzanero press --label Settings --device <UDID>
```

- **The display is external.** An Apple TV reports one primary display of type `external` (`TVOut`, the television) with `backlightState: off` whether or not it is drawing. So `readiness` and the screenshot receipt say `displayPower: external`, with no advice to wake it and no "probably black" note, and `tree`, selector actions and waits accept that display. Whether the television itself is on cannot be read.
- **The foreground application is the frontmost one.** The centre hit test a phone uses was refused there (error 8), so on an external display the tree asks for the frontmost application, as the simulator route does; the result says `selection: frontmost`. The tree marks the focused node, as on the simulator.
- **Points.** The display information gives 3840 × 2160 pixels at point scale 1, while the tree's frames fill 1920 × 1080. An external display's bounds are therefore taken as 1920 points wide, and the result's `display` says so. A 4K Apple TV simulator (`Apple TV 4K (3rd generation)`, not the "at 1080p" type) reports the same values with the same tree, and `displays` there now lists 1920 × 1080 points at scale 2 instead of 3840 × 2160 at scale 1.
- **`set-value` opens the keyboard on a simulator.** After `set-value` on the probe's text field the tvOS full-screen keyboard was in front, so the app's elements read `visible: false` and `press` was refused until `remote menu` closed it. On the device the next command had been `remote home`, so whether the keyboard opens there too was not seen.
- **`remote` routes.** The arrows and `select` are the keyboard usages the simulator command sends, and `home` is consumer usage 0x40. `menu` is the Escape key (usage 41): the device's button service closed the connection on the consumer usage 0x46 the simulator takes, and Escape went back one level. `play-pause` is the Space key (usage 44), because the same service closed the connection on 0xCD. The [tvOS probe](probe-app.md#tvos-probe), installed on the device, recorded `play-pause`, `select`, `menu`, `up`, `left` and `right` as sent; `down` and `home` were seen by their effect. On the Home Screen play-pause may start audio, so send it only where its effect is wanted. `remote` reads the device's details first and is refused on a device whose type is not `appleTV`.
- **Touch is refused** with the pointer to `remote`, after the display read and before any input. `wake` presses nothing and answers `external-display` with exit 1: there is no side button. `remote home` left the screen saver.
- **`key` and `button home`** work as on a phone. A `key right` sent over the screen saver changed nothing visible.
- **Recording and `frames` are refused.** With the external display let through once, `frames` saved three images and `record --backend coredevice` a 5-second movie, both 3168 × 1792 and both wrong: a black rectangle about three quarters of the width on a grey ground, while a screenshot at that moment showed the Home Screen. The device sent almost nothing: 16 packets for 14 frames of that size, and 272 kB for three saved images, so the picture was blank when it left the Apple TV and the decoder is not what lost it. Why the device sends a blank picture is not known (protected output is one guess). Both now answer `unsupported-operation` before any stream starts; `screenshot` works. A lead from 2026-11-19: Apple's Device Hub, watched in the Mac's log while it showed this Apple TV's screen, asks for the video exactly as this tool does (the same media stream actions, `CoreDeviceVideoDisplayMode: DisplayByID`, display 1, supported features 140, TCP, 3168 × 1792 at 60 frames a second), but it starts an audio stream first, in the same client session, and gives each start a session event channel; this tool starts the video alone ([record](verification.md#device-hubs-screen-view-of-the-apple-tv)). Device Hub's picture was correct. Whether the missing audio stream is what leaves this tool's picture blank has not been tried; it is a pending task.
- **`set-value`** put `héllo tv` into the probe's SwiftUI text field, and the app's own bound text read the same. `select` on a focused text field opens tvOS's full-screen keyboard, where the arrows move among its keys and Menu closes it.
- **Power.** `button lock` (consumer usage 0x30, held 400 ms) woke the Apple TV from its screen saver; with the Home Screen in front it opened Control Centre with Power Off in focus, and `remote select` then put the device to sleep. Control Centre is not in the tree (the frontmost application is `PineBoard`, with no nodes for it), so the focus was read from a screenshot. Asleep, the device still answered `readiness` and the display query, with the same display values as awake, and `screenshot` failed with "Display reports zero-sized native size" (CoreDevice error 25005), which is the one sign of sleep found. `readiness` did not wake it. One `remote home` does: sent alone to the sleeping device, it was followed four seconds later by a screenshot of the Home Screen, and the human owner saw the television come on with the Apple TV ([record](verification.md#the-apple-tv-4k-what-wakes-it-and-why-its-connection-goes-stale)).
- **The connection goes stale.** Three times on 2026-11-18 every query to the Apple TV began to time out while the Mac still listed it as connected, until `remotepairingd` and `CoreDeviceService` were restarted with the human owner's word. The Mac's `remoted` logs "Device connection interrupted" for a device many times a day and normally "Handshake complete" within a second, for the phone as well, and around `devicectl`'s own assertions. Each stale period began with an interruption that was never followed by a handshake; from then on `remoted` logs "Heartbeat failed: not connected" every 30 seconds and does not try again. Two began as a `tree` was starting and one just after the device was put to sleep. Presenting another peer identity in manzanero's own directory handshake did not prevent the interruption on the phone.

  On the night of 2026-11-18 it happened three more times, and the logs were read each time before anything else ([record](verification.md#the-apple-tv-4k-what-wakes-it-and-why-its-connection-goes-stale)). What they show:
  - **The trigger is this tool's accessibility route.** `tree`, `wait`, `press`, `scroll` and `set-value` open the tool's own connection to the device's service directory. Between 0.1 and 0.3 s after each, `remoted` logs `Connection reset by peer` on its own connections to that port and then `Device connection interrupted`. It reconnects at once; most times `Handshake complete.` follows within 0.1 to 1.2 s, and now and then it never does. About 25 accessibility commands passed between a restart and the next stale period.
  - **Only queries break.** In the stale state `devicectl` queries time out ("Command timeout of 10.0 seconds exceeded"), so `tree`, `screenshot`, `readiness`'s display state and everything that reads the display fail. Input still arrives: `remote`, `key` and `button` were dispatched in 1 to 2 s, and the human owner drove the device from Device Hub meanwhile. The tunnel keeps carrying packets.
  - **How to see it without touching the device.** Apple's `remotectl dumpstate` lists the connection as `State: attached` with `No connect() results` instead of `State: connected (connectable)`. A query that times out in that state now says so in its error (`StaleDeviceConnection`), and tells the caller not to retry.
  - **How it ends.** The stale connection lasts as long as its tunnel, and the tunnel lasts while any process holds a usage assertion on it. Every command takes one, so retrying keeps it stale. Left alone it cleared once after two and a half minutes and once within about a minute; another time, with Device Hub and Xcode open, it stayed stale for over forty minutes, until `remotepairingd` and `CoreDeviceService` were restarted on the human owner's word.
  - **What did not prevent it.** Closing the tool's directory connection as soon as the accessibility socket was connected; and, again, an identity of the tool's own in the handshake, with which the resets continued and half of the tool's own commands failed with "Accessibility socket send: Broken pipe". Both were taken back out.
  - **Why the tool cannot do as Device Hub does.** Asked by this process for the accessibility service of the device, `remoted` logs `Client lacks privilege to find service with name com.apple.accessibility.axAuditDaemon.remoteAXService`; it hands the same service to `CoreDeviceService`. `remotectl netcat` to the service is granted the lookup and then fails to connect. The route through `CoreDeviceService` was then looked at again and is closed as it stands: its socket request opens CoreDevice's own services by name and answers POSIX 83 for the accessibility service and for every shim service, before any packet leaves the Mac. `remoted` lets a client connect only with the entitlement the device's directory names for the service, and for the accessibility service the device names `AppleInternal`, which no process on a customer Mac satisfies. The tool's own directory connection therefore stays the only route ([transport](transport.md#the-cost-of-this-route), [record](verification.md#asking-coredeviceservice-for-the-accessibility-socket)).

  - **What is built against it.** The device's directory is read once per tunnel, and commands after that connect straight to the accessibility port: from memory within a process, from a small file in the user's Application Support across processes. A `batch` of 30 accessibility steps caused one reset instead of thirty, and ten separate CLI commands on a tunnel already known caused none ([record](verification.md#one-directory-connection-per-tunnel)). And an accessibility command on a connection that is already stale is refused as `device-not-ready` before it takes the assertion that would keep it stale. Neither ends the fault: every new tunnel still costs one directory connection, and the tunnel is replaced some seconds after the last command when nothing else holds the device.

  That the device keeps one directory peer per tunnel is an inference from these timings. Why `remoted`'s reconnect sometimes never completes is not known.
- **`type`** appended ` abc` to the probe's focused text field with tvOS's keyboard closed; the space was typed, not taken as play-pause.
- **No hit test on an Apple TV.** `press`, `set-value` and the check after `scroll` normally ask the device which element is under the target's centre. An Apple TV has no pointer, and on a tvOS simulator that question was answered by the system process (`PineBoard`) for a list row just inside the bottom edge, so `scroll` moved the list and then reported `postcondition-failed`. On an Apple TV, physical or simulated, these commands now check only that the target is visible with its centre on the display. With that, on the simulator, three `scroll` calls each brought the next row of the [tvOS probe](probe-app.md#tvos-probe)'s forty-row list into view as `postcondition-verified`, and `press` on the bottom row was recorded by the probe. Not run on hardware.
- **`scroll` reaches only what the tree holds.** The probe's list had 13 of its 40 rows in the tree at first, and each `scroll` to the last of them added one more. `scroll --search` does that walk in one command ([guide](direct-accessibility.md#searching-a-list-that-loads-its-rows---search)); on the simulator it reached row 35 in 22 steps. In Settings › Accessibility the rows below the screen's edge are not in the tree at all, so no selector can name them; move focus down with `remote down` instead. `scroll --label Motion`, on a row already on screen, answered `postcondition-verified` with `nativeResult: false` and moved nothing. Each row there appears several times in the tree, once as a visible cell and again as inner texts marked `visible: false`, so read `visible` on the cell.
- **Run on the device on the night of 2026-11-18**, with the probe's current build (built and signed with what was already on the Mac, no provisioning change): `scroll` on a row; `scroll --search` down (row 35 in 8 steps, row 30 in 8), right (column 28 in 16) and left (column 1 in 18), each verified; a search up that reached row 1 in 23 steps and then failed its last check, explained on 2026-11-19 (a long search ran out of the session's frame allowance, which now grows with the steps; up from row 40 to row 1 then ran in 28 steps, twice: [record](verification.md#apple-tv-4k-with-the-tunnel-as-the-default-and-the-search-up)); `press` on a found row and on the row at the bottom edge, each recorded by the probe; `press --label Twin --index 2` and `--index 1`, recorded as `select:twin-2` and `select:twin-1`; a `batch` of two remote presses, a wait and a press, recorded as `select:c`; `set-value`, which set the field and left tvOS's keyboard in front until `remote menu`, as on a simulator.
- **Not shown:** `remote --hold` and swipes on the device (both refused there), recording and `frames` (refused; the opt-in media probe could not run because it sends a tap), and an app of the owner's own.

### Focus in the tree and in waits

On an Apple TV simulator, `tree` (and `screen`'s tree) asks the application for its focused element once more after the snapshot and marks that node `"focused": true`; the result also has `"focus": {"read": true, "attribute": 19, "nodeId", "label", "identifier"}`, with nulls when the focused element is not among the snapshot's nodes. No existing field changes, and other families send no extra request and get no `focus` key.

`wait … --until focused` is met when exactly one visible element matches and its live focused attribute is true; the reason is `not-focused` or `focus-unknown` otherwise. It reads the focused attribute together with the enabled and visible attributes it already reads; other conditions send exactly the requests they did before. It is accepted on every platform, but has only been checked on the Apple TV simulator. On tvOS, `remote` moves focus and `select` activates the focused item, so a `wait --until focused` between them confirms the target before the click.

How the attributes were found: the snapshot's attributes and the traits of the focused and unfocused buttons were identical. `-[AXPMacPlatformElement _attributeTypeForMacAttribute:]` in AccessibilityPlatformTranslation maps `AXFocused` to attribute 28 and `AXFocusedUIElement` to 19 (`AXFrame` 21, `AXIdentifier` 25, `AXEnabled` 27 and `AXValue` 53 match the attributes Manzanero already used). On the tvOS probe, 28 answered true for the focused button and false for the others, and 19 on the application answered the focused button's element.

### Remote touch surface

`remote swipe-up`, `swipe-down`, `swipe-left` and `swipe-right` (the same names in MCP `press_remote`) draw one finger across the Siri Remote's touch surface, on Apple TV simulators only.

How it is sent. The simulator's `com.apple.coredevice.feature.remote.universalhidservice` takes a `createService` request whose `_0` is a HID service description in the shape `connectedServices` lists them. The tool asks for one touch-pad service for the call: `_ServiceID` 0x700, `PrimaryUsagePage` 13, `PrimaryUsage` 5, a `Product` name and one `DeviceUsagePairs` entry. The daemon answers `{serviceID: 1792}`, and `backboardd` logs the new service as `eventSource: externalAccessory; primaryUsagePage: 0xD; primaryUsage: 0x5`. The swipe then goes to that service ID as the same 58-byte reports multi-touch uses on a phone, through the same scheduler: a contact that goes down a quarter of the surface before the centre, moves through it in ten frames 20 ms apart, and lifts a quarter past it. `backboardd` delivers them to the frontmost app as pointer and game-controller events. The daemon cancels the service when the connection closes; nothing is left behind. A description without a primary usage is refused (CoreDevice error 15001), and `removeService {_0: UInt64}` exists and is not used.

What it does, on a tvOS 27.2 simulator at 1080p against the [tvOS probe](probe-app.md#tvos-probe) on 2026-11-18, the focus read from the tree after each: a swipe moves focus several items, where an arrow moves one. In the probe's list, `swipe-down` took the focus from row 3 to row 7 and from row 7 to row 11, and `swipe-up` back from row 11 to row 7. From Button A, `swipe-down` reached the text field, three elements below; `swipe-up` from there reached Button B. `swipe-right` from the controls entered the list, and `swipe-left` returned to the controls; each of the two was repeated with the same result.

Limits: the travel and the speed are fixed, so how far the focus goes is the app's doing; `--hold` is refused with a swipe; nothing is known about a click of the surface or its clickpad ring; a sleeping simulator ignores swipes as it ignores buttons. On a physical Apple TV a swipe is refused as `unsupported-operation` before any contact: no route for creating a HID service on a device has been looked for.

How it was found. What was tried first on the tvOS 27.2 simulator, with a scratch probe sending raw XPC to the simulator's `dtuhidd`:

- `com.apple.coredevice.feature.remote.universalhidservice` (the route multi-touch uses on phones) lists only `mainTouchscreen` (`CoreDevice touchscreen(nil)`, usage page 13/4), `mainKeyboard`, `mainScreenButtons` and `avpCustom`. Its `Request` enum has no `connect`, `report` or `supportedDevices` case: each was refused as `DecodingError.typeMismatch … Request … Invalid number of keys found`.
- A second feature, `com.apple.coredevice.feature.remote.universalhid` (logged as `LegacyUniversalHIDServer`), does have them. `{supportedDevices: {}}` answered six device kinds, beginning `appleTVRemote`, `digitizer`, `mouse`. Its decoding errors gave the request shapes: `connect: {_0: {vendorID: Int, productID: Int, product: String, usages: [{page: UInt16, code: UInt16}]}}` and `report: {_0: UInt64 service ID, _1: Data}` (a raw HID report).
- `connect` with usages page 12/1 (consumer control) or page 13/5 (touch pad) created and activated a virtual HID service, named `unknown(0x0)` in the log, but the reply failed on the daemon's side (`NSCocoaErrorDomain` 4866, "The source for an in-place encode must encode to a dictionary at the top level"), so the new service's ID never came back, and the service was cancelled when the connection closed.
- That looked like a dead end on 2026-11-16. On 2026-11-18 the same `connect`, sent with its usages as unsigned integers, answered the 4866 error as a reply and the virtual service was not listed by `connectedServices`. The way through was in the daemon's own log: its newer server reported an error handling a `removeService` request, which named a case the 2026-11-16 pass had not tried. Sending `createService` and `removeService` with an empty body returned decoding errors that gave their shapes, and `createService` with a touch-pad description worked at the first attempt. The legacy `universalhid` route and `com.apple.coredevice.feature.remote.hid.tvremote` are not used.

## Digital Crown and side button (Apple Watch)

```sh
manzanero crown <units> [--events <n>] --simulator <UUID>   # negative: crown --simulator <UUID> -- -200
manzanero button side --simulator <UUID>
manzanero button action --simulator <UUID>                  # Apple Watch Ultra's Action button
```

`crown` sends `IndigoScrollEvent` messages to the simulator's `com.apple.coredevice.feature.remote.hid.scroll` service, which only watchOS runtimes publish: `{point: {x: 0, y: <units>, z: 0}, phase: 0, momentum: 0, target: 0}`. Target 0 is the Digital Crown (target 1 is refused as `No dial service found for scroll event`).

Calibration on the watchOS 27.2 simulator, with a SwiftUI probe whose `digitalCrownRotation` value (low sensitivity, continuous) was read through the tree, and with Watch Settings' list:

- **Units are integers.** `y: 1` moved the value by 0.005, `1.5` by 0.005, `0.5` not at all: the daemon drops fractions. So 200 units are 1.0 of a low-sensitivity SwiftUI binding; positive values increase it and scroll lists toward later content, negative ones back.
- **Single events are exact, at any size** (`y: 1000` moved it by 5.000). **Fast events are accelerated**, like a crown turned quickly: five 20-unit events 16 ms apart moved the value by 4.8 instead of 0.5, 100 ms apart by 2.6, 200 ms apart by exactly 0.5.
- **Lists move by rows per event, not by units.** In Watch Settings one event of 100 units or more moved the list one row (24 points for the first, then 60), whatever its size (100, 300 and 1000 alike); events below 100 (20 or 50 units, even repeated) moved nothing. Two 100-unit events 250 or 500 ms apart moved it more than four rows, 800 or 1200 ms apart exactly two.
- **Phase and momentum.** Phases 1 (began), 2 (changed) and 4 (ended) each delivered their delta like phase 0, but a began–changed–changed–ended sequence of 30 units moved the value by 40 units' worth, so the ended phase adds an inertial step. Momentum 1 or 2 made no difference. Manzanero sends phase 0 and momentum 0.

So `crown` sends the units as the fewest events of at most 1000 units, one second apart, and `--events <n>` (1...20) splits them evenly: `crown 200` moves a SwiftUI crown binding by 1.0, and `crown 300 --events 3` moved Settings three rows. The receipt lists `unitsPerEvent`. Several events take one second each. Another family is refused as `unsupported-operation` before input, and a physical device before any contact.

**Side button.** DeviceKit's watch chrome (`/Library/Developer/DeviceKit/Chrome/watch*.devicechrome/…/chrome.json`) gives the side button as consumer page 12, usage 149 (0x95), and the crown press as 64 (the existing `button home`). `button side` sends 0x95 on the button service; on the watch face it opened Control Center, and a second press closed it. It is refused on other families. `button lock` (0x30) still does nothing on the watch.

**Action button.** The `watch6` chrome, the Apple Watch Ultra's, also lists a `left-side-button` (image `StingButton`) on the vendor page 0xFF01, usage 512 (0x200). `button action` sends that pair on the button service, held 80 ms. On an Apple Watch Ultra 4 simulator's watch face it opened the Action button's setup ("Choose Action"); on a Series 12 simulator, which has no such button, the same event changed nothing. It is sent to any Apple Watch simulator and refused on other families; the receipt and the dry-run plan give `usagePage` and `usage`.

**No keyboard input.** `key` and `type` are refused on an Apple Watch simulator as `unsupported-operation`, before any input. The keyboard service accepts the events, but nothing arrives: `key down`, `key return` and `type 12` changed nothing in Calculator, and with the system text entry sheet of a SwiftUI `TextField` open, `type 'Hola 12'`, `key backspace` and `key return` left the field empty and the sheet open. `set-value` on that field was acknowledged and changed the text the field shows and reports, but the app's bound string stayed empty, so on watchOS it is not a way to enter text either. The sheet's own keys can be tapped.

MCP: `rotate_crown`; `press_button` accepts `side` and `action`.
