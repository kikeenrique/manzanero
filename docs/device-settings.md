# Orientation, settings, location, status bar and clipboard

Five commands that change or read a target's state through Apple's `devicectl`, which addresses a booted simulator by its UUID exactly as it addresses a device. Built on 2026-11-21 and run on an iPhone simulator (`manzanero-research-phone`, iOS 27.2); on the iPhone 13 mini the same evening `rotate`, `location`, `clipboard` and `settings` (read, changed and put back exactly) worked, and `status-bar` is not supported by a device ([record](verification.md#phone-session-of-2026-11-21-the-days-new-commands-landscape-and-a-recording)). On a device each command but `clipboard` changes the human owner's device, so ask first.

```sh
manzanero rotate landscape-left --simulator <UUID>          # portrait, portrait-upside-down, landscape-left, landscape-right
manzanero settings --appearance dark --text-size accessibility-large --increase-contrast on --reduce-motion off --simulator <UUID>
manzanero location 40.4168,-3.7038 --simulator <UUID>
manzanero location --simulator <UUID> -- -33.8688,151.2093  # a coordinate that begins with '-' goes after --
manzanero location --clear --simulator <UUID>
manzanero status-bar --time 9:41 --battery-level 100 --battery-state charged --wifi-bars 3 --simulator <UUID>
manzanero status-bar --clear --simulator <UUID>
manzanero clipboard --simulator <UUID>                       # read-only
```

MCP: `device_settings` (`operation`: `rotate`, `settings`, `location`, `status-bar`, with the same values as fields) and `read_clipboard`, which is read-only.

| Command | devicectl | Notes |
| --- | --- | --- |
| `rotate` | `device orientation set` | The interface turns only as far as the app in front allows: read the tree afterwards (its `screen.orientation` on a simulator). Accessibility commands follow the turn on a simulator; on a phone they accept it since 2026-11-21, and `tree`, `press`, `set-value`, `scroll --search` and `tap` ran in both landscapes on the iPhone 13 mini that evening ([accessibility](direct-accessibility.md#current-native-tree-route)) |
| `settings` without options | `device info appearance` | Read-only: the current `userInterfaceStyle`, `textSize` (written "Extra Small", "Large"…), `increaseContrast`, `reduceMotion`, `reduceTransparency`, `largerAccessibilitySizesEnabled` and others, so a change can be put back exactly. Read on the iPhone 13 mini and a simulator on 2026-11-21; on the simulator a change to dark and Small read back as such and was put back to light and Large. MCP `read_settings` |
| `settings` | `device settings appearance` | `--appearance light\|dark`, `--text-size` (the twelve sizes, from `extra-small` to `accessibility-extra-extra-extra-large`), `--increase-contrast on\|off`, `--reduce-motion on\|off`; an accessibility text size also turns Larger Accessibility Sizes on, which devicectl requires for those sizes |
| `settings --voiceover on\|off` | `device settings voiceover --enable` / `--disable` | Alone, in a call of its own (since 2026-11-23). VoiceOver changes how every touch is taken, so turn it off again after a check |
| `settings --standby show\|hide` | `device settings standby --show` / `--hide` | Alone, in a call of its own (since 2026-11-23); `--standby-seconds 1…600` with `show` keeps StandBy up that long and waits (devicectl's own timeout is set 30 s longer). Apple presents StandBy only from the lock screen |
| `settings --biometrics on\|off\|state` | `device settings biometrics --enable` / `--disable` / no switch | Alone, in a call of its own (since 2026-11-24). `on` enrols Face ID (or Touch ID), so an app's biometric prompt can appear, for example to be answered by a person in a `handoff`; `off` removes it; `state` reads each type and whether it is enabled, read-only (MCP `read_settings` with `biometrics: true`). On a simulator only, `match` and `nomatch` answer the prompt on its screen with a matching or a non-matching face (or finger): `simctl spawn <UUID> notifyutil -p com.apple.BiometricKit_Sim.fingerTouch.<outcome> -p com.apple.BiometricKit_Sim.pearl.<outcome>`, the notifications the simulator's BiometricKit listens for; a device is refused, since its sensor takes only a real face. A failed match leaves Face ID's own alert, in `LocalAuthenticationUIService`'s tree with identifiers that do not depend on the language: `com.apple.localauthentication.ax.authentication.button.cancel` and `….button.try-again`, pressed with `--pid` of that process |
| `location` | `device simulate location coordinate` / `clear` | Decimal degrees, latitude −90…90 and longitude −180…180 |
| `status-bar` | `device simulate statusBar override` / `clear`, simulators only: the iPhone 13 mini answered that the capability is not supported, so a device is refused before it is contacted | `--time` (text), `--battery-level 0…100`, `--battery-state draining\|charging\|charged`, `--wifi-bars 1…3`, `--cellular-bars 1…5` (each also sets its mode to active), `--data-network` (hide, wifi, hotspot, 1x, GPRS, Edge, UMTS, 4G, LTE, LTEA, LTEPlus, 5G, 5GPlus, 5GUWB, 5GUC) |
| `clipboard` | `device pasteboard paste` | The first item's text, at most 1 MiB, with `contentType` and `bytes`; `empty: true` when there is nothing. devicectl writes the text to its stdout and its JSON to a file of the run, which is deleted afterwards |

Every command has a `--dry-run` plan, the invocation above, and each value is checked before any device is contacted. On a device, each first checks Developer Mode as `launch` does.

## Observed on the simulator

2026-11-21, `manzanero-research-phone`: `rotate landscape-right` made the tree report `rot90` and `rotate portrait` `rot0`; through `devicectl orientation set` directly, `landscapeLeft` gave `rot270` with an 874×402 interface, and in that orientation a `press` of a list row of the probe was accepted and recorded by the probe. `settings --appearance dark --text-size accessibility-large --increase-contrast on` read back from `simctl ui` as `dark`, `accessibility-large` and `enabled`, and the reverse as `light`, `large` and `disabled`. `location` with a negative longitude and `--clear` succeeded. `status-bar --time 9:41 --battery-level 100 --wifi-bars 3` and later a battery level of 7 while draining read back from `simctl status_bar list`; `--clear` removed them. `clipboard` returned the text a `devicectl pasteboard copy` had put there (`hola café`, 10 bytes, `public.utf8-plain-text`).

2026-11-23, the same simulator: `settings --voiceover on` and `off` each answered success, and the simulator's `com.apple.Accessibility` `VoiceOverTouchEnabled` read 1, then 0. `settings --standby hide` answered success; `--standby show --standby-seconds 3` failed with Apple's "StandBy can only be presented while the device is showing its lock screen" (CoreDevice error 1001), since the simulator was unlocked. On the iPhone 13 mini on 2026-11-24 `--voiceover on` and `off` each answered success; the first switch-on showed VoiceOver's gesture explanation ("Gestos de VoiceOver", dismissed with `press --label Aceptar`) and then VoiceOver's own notification permission prompt, answered "No permitir" by the human owner's choice: switching VoiceOver on a device for the first time leaves both on its screen ([record](verification.md#phone-session-of-2026-11-24-handles-the-cost-of-a-tree-symbols-and-voiceover)). StandBy cannot run there: on 2026-11-24, with the phone charging on its lock screen, `--standby show` was refused by Apple's tool, "The capability 'StandBy' is not supported by this device" (CoreDevice error 1001), and the phone's capability list has no `com.apple.coredevice.feature.standby` ([record](verification.md#standby-on-the-phone-refused-by-the-device)). Later on 2026-11-23 the same simulator's accessibility snapshots of the probe came back empty until it was restarted; whether the VoiceOver switch caused it is not known ([record](verification.md#hold-on-a-simulator)), so restart a simulator after switching VoiceOver if its trees fail. On 2026-11-24 `settings --biometrics state` read Face ID as disabled on that simulator, `on` and `off` answered with the new state, each read back by `state`, and it was left as it was found, off; later that day the iOS probe's [biometric button](probe-app.md#biometric-probe) checked it: with Face ID enrolled a press of `probe.biometrics.request` raised the system's Face ID prompt; `settings --biometrics match` answered it (`success`); after `nomatch` the "Face Not Recognized" alert was waited for and its Cancel pressed by identifier in `LocalAuthenticationUIService` (`failed:-2`, LocalAuthentication's user cancel); enrolment was put back off ([record](verification.md#a-face-id-prompt-on-a-simulator)). On the iPhone 13 mini on 2026-11-24 `devicectl` listed no biometric type and changed nothing, though it answered success; the result says so since (`biometricsSupported: false`, `changed: false`, [record](verification.md#biometrics-on-the-phone-no-type-to-control)). `devicectl device settings audio` (output and input device, volume) is not exposed: the room the Apple TV is in stays quiet, and a phone's volume is the human owner's.

The same route put text on the simulator's clipboard, which `simctl pbcopy` never did. Simulator `paste` still stays refused: the Command+V after it, sent through the simulator's keyboard service, inserted nothing ([simulator paste](simulator-input.md#unicode-text-set-value)).
