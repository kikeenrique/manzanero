# Roadmap

The goal is a Swift CLI with broad Apple-device inspection and control, plus an optional MCP server that shares the same operations. iPhone, iPad, Apple Watch, Apple TV and iPhone Duo are in scope; physical controls and the observe → act → inspect loop come first.

This page has two halves: what exists today and how far it has been checked, and what is still to do. [Feature status](feature-status.md) is the compact inventory per area, the [live check plan](live-check-plan.md) lists the runs still owed on hardware, and [verification](verification.md) is the dated record of what was observed.

Verification levels used below:

- **iPhone 13 mini**: run on the one test phone (iOS 27.2.1, macOS 27.2.1, Xcode 27.2), in portrait. One phone and one OS version; not a general reliability claim. It had no passcode until the evening of 2026-11-17 and has one since.
- **Simulators only**: run on the named simulators (iOS, tvOS or watchOS 27.2 runtimes); nothing known about the hardware.
- **Unit-tested only**: local tests and dry runs; never run against a device.

## Pending

The order below is a suggested order, not one the owner set. It follows the standing priorities of this page: dependable physical testing first, then coverage of more devices, then the gaps in other families, then delivery. The first group is for choices that unblock an item further down.

### Decisions waiting for the owner

None at the moment. Decided on 2026-11-17 and 2026-11-18 and listed with the [decisions](#owner-decisions-2026-11-17) below: `press` on an element partly off the display, a selector by value, a PID for the browser around a page, one experiment with an offer that asks for RTCP feedback, and physical `logs`, which is now a [pending task](#not-built).

### Dependable physical testing

6. **Handoff: finished on this phone and host.** Every ending has run with a person: `unlocked`, `paired` and an element condition observed, a timeout, a typed decline while watching, the MCP `until` field, and the form's Accept, Decline and Cancel ([record](verification.md#the-last-handoff-runs-on-the-phone)). What is left needs other equipment: a second MCP host, and a real biometric prompt (the test phone has no Face ID set up; the passcode gate of Settings ran in its place). Whether a host removes a form the server withdraws is untested, so a watching handoff shows no form.
7. **Web content: what is left.** Checked in Chrome only: Safari and an app's own `WKWebView` are unrun, and so is `scroll` on a page. Two changes of 2026-11-17 are unit-tested and still owe a run against a browser on the phone: `press` on a field wider than the display, and a selector action on the browser's own controls with `--pid`. The first read after a page load can select the browser instead of the page; how often is not counted. `set-value` is acknowledged by a web input and does not change it (press it and `type`).
8. **A phone in landscape.** `tree` and every selector command refuse it ("native AX centre selection requires portrait geometry"), seen on 2026-11-17. Touch, keys, `frames` and recording in landscape are unrun on hardware; rotation was measured on simulators only.
9. **Recording startup and recovery.** Crash and disconnect recovery are not built, and are to be a restart of the stream: keyframe requests were dropped after the phone declined an offer that asked for RTCP feedback. Earlier startup failures were traced to the macOS firewall in one case; whether that explains all of them is open. `rtcp.negotiatedFeedback` has been read in three recordings, `disabled` each time.
10. **Release after failure.** Quarantine is built and ran on a simulator and the phone, where a killed process's contact ended by itself. Still unobserved: a held key or button whose sender is killed, and a lost cable or network path mid-input, which reaches quarantine only if the bridge reports an unknown outcome. The mark's `since` time is when the next input was refused, not when the owner died.
11. **Open questions on the phone.** One tap on the Settings search field had no effect while 36 others did; Apple's device services stopped answering once on 2026-11-16 (`mise run diagnose:device-services` captures the evidence before a restart next time). Neither has recurred. An unconfirmed subscription stop recurred on 2026-11-17, three times among about thirty selector commands: each time the socket closed 2 to 3 ms into the stop exchange after one cleanup frame, so the phone closed first; whether that is harmless is not settled. Setting a passcode dropped the pairing once; whether it always does is unknown. A mode in the touch runner that compares the tree before and after each action, to catch the next missed tap with evidence, is not built. See the [live check plan](live-check-plan.md#questions-still-open).
12. **Small faults found on 2026-11-17: fixed that night, partly unrun.** A secure field's bullets are reported as a masked read-back instead of a mismatch (unit-tested; not repeated on the phone). `detect-layout` takes `--index` (run on a simulator). A screenshot of a sleeping phone still succeeds, and its receipt says the display was off (seen on the phone).
13. **Unclassified failures.** Errors that are not `CommandFailure` now get a category when their type and domain are recognised (decoding, POSIX, URL, file and AVFoundation errors); the rest still report `unclassified` ([errors](errors.md#unclassified-sites)). None of these has been provoked on a device.

### More devices and more apps

14. **A second iPhone and an iPad.** Everything physical ran on one iPhone 13 mini; iPad was measured on a simulator only. The 200 ms input drain was measured on that phone alone.
15. **`set-value` in more fields.** It ran in the probe's field, in a UIKit text field and a secure field in Settings, and through MCP. A SwiftUI field with a label or identifier is untried.
16. **`--index` on a simulator and through MCP against a device.** It ran on the phone from the CLI, on a web form.
17. **Keyboard layouts on a phone.** Only Spanish – ISO, the layout the test phone uses on its own, has been typed and detected on hardware. A phone's layout cannot be read; `detect-layout` is the substitute. Whether a phone applies the ISO or ANSI table to the 13 layouts where they differ is unchecked.
18. **`frames` beyond one portrait phone.** Other devices, long runs toward the 1000-frame and 1 GiB limits, and a second process competing for the stream.
19. **What apps' recognizers make of three to five contacts.** Delivery is measured; recognition in real apps is not.
20. **`console` above its default bound.** An output above 64 KiB has not been produced: the probe app has no bulk trigger.

### Other families

21. **Real Apple TV, Apple Watch and iPhone Duo hardware.** Everything in [other families](other-families.md) has run on simulators only; on hardware nothing is known.
22. **Apple TV remote touch surface.** Blocked: the simulator's `universalhid` service creates a virtual device but fails to encode its reply (`NSCocoaErrorDomain` 4866), so the device's ID never comes back and no swipe can be addressed ([details](other-families.md#remote-touch-surface-not-built)).
23. **Text entry on Apple Watch.** Keyboard events do not reach watchOS, so `key` and `type` are refused there, and `set-value` changed a SwiftUI field's text without changing the app's bound value ([details](other-families.md#digital-crown-and-side-button-apple-watch)). The remaining route is tapping the text entry sheet's own keys, which is not built.
24. **iPhone Duo gaps.** The Home Screen tree comes back empty on the Duo runtime, folded and unfolded: SpringBoard answers no snapshot at any depth there, so only OCR reads that screen; recheck on the next runtime. On the inner display, four- and five-path `multi-drag` ran on 2026-11-17; the centre-hit fallback (for a simulator that reports no frontmost application) has not, and only one orientation was seen. A portrait-only app is letterboxed there, in a window 469 points wide: its tree's frames are relative to that window, so `press` fails at the hit test (error 8), and touch coordinates are the display's, not the window's ([record](verification.md#the-duos-inner-display)); mapping frames by the window's origin is not built. One `fold` in five was not observed within its 10 s bound on a Mac with three other simulators booted; with two others booted, five of five were. It has not run with nothing else booted. A label shown in both columns of a two-column layout is ambiguous; `--index` now chooses, and has not been tried there.

### Not built

- **`logs` for physical devices.** Pending since the owner's word on 2026-11-18. It is refused as `unsupported-operation` today, and it is the only way to an app's debug-level lines on a phone, because `console --os-log` mirrors info and above. The route is the native `os_trace_relay` service ([research](app-logs-research.md), section P-B), and two experiments showed it works on the test phone: the service is a plain, unencrypted shim, and a bounded stream for one PID delivered the probe app's lines at every level over the native tunnel ([record](verification.md#the-log-relay-on-the-phone)). The opt-in task `test:os-trace-relay` and the bridge's shim-port function are the starting point. Still to build: the command with the options simulator `logs` has, a bound on raw bytes received as well as entries kept, filtering by subsystem, category and level on the Mac, bundle-to-PID resolution and what to do when a relaunch changes the PID, a dry-run plan, the MCP mapping, and the `doctor` and dependency notes. Still to learn on the device: long streams, a stream of every process, and records with unusual fields.
25. **Simulator `wake` and `paste`.** Both are refused as `unsupported-operation`; `simctl pbcopy` did not reach the simulator's pasteboard, so `set-value` is the Unicode route there.
26. **Agent features.** Durable sessions, reusable element handles, symbolication, `.xcappdata` export, build progress and a build deadline. Prompt detection exists only in the form a caller asks for: `handoff --until gone` on a prompt's button. Nothing notices a prompt by itself.

### Delivery

27. **Beta release and Homebrew tap.** The release workflow passed its rehearsal on 2026-11-18: a manual run built, tested and packaged 0.1.0-beta.1 and uploaded `beta-dist` without publishing ([record](verification.md#release-rehearsal)); its one earlier run had failed before the CI fixes. Still to do: the [public-readiness review](public-readiness.md), the tag that publishes, and a real Homebrew install of the tap formula. The archives are ad hoc signed and not notarized ([releasing](releasing.md)).

## Architecture constraints

Device operations communicate with Apple frameworks/APIs from this project's code or Apple executables. Non-Apple device helpers remain blocked. Use maintained general-purpose libraries where useful, and preserve attribution for implementation references.

Keep private interfaces behind backend boundaries. Avoid automatic replay of input or a fallback that changes the operation's semantics. Surface native acceptance, observed effect and cleanup as separate facts.

## Implementation references

Independent protocol references and their licenses are documented in [dependencies.md](dependencies.md). The capability inventory distinguishes those references from this project's implemented routes and live verification.

## Completion criteria

A build or dry run proves planning/compilation, not hardware behavior. Completion requires evidence for the claimed platform, device family, transport and operation, including material failure and interruption cases. A returned receipt alone cannot establish UI effect, exact contact delivery or release.
