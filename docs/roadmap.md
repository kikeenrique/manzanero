# Roadmap

The goal is a Swift CLI with broad Apple-device inspection and control, plus an optional MCP server that shares the same operations. iPhone, iPad, Apple Watch, Apple TV and iPhone Duo are in scope; physical controls and the observe → act → inspect loop come first.

This page has two halves: what exists today and how far it has been checked, and what is still to do. [Feature status](feature-status.md) is the compact inventory per area, the [live check plan](live-check-plan.md) lists the runs still owed on hardware, and [verification](verification.md) is the dated record of what was observed.

Verification levels used below:

- **iPhone 13 mini**: run on the one test phone (iOS 27.2.1, wired, macOS 27.2.1, Xcode 27.2). One phone and one OS version; not a general reliability claim.
- **Simulators only**: run on the named simulators (iOS, tvOS or watchOS 27.2 runtimes); nothing known about the hardware.
- **Unit-tested only**: local tests and dry runs; never run against a device.

## Pending

The order below is a suggested order, not one the owner set, except where an item says the owner decided. It follows the standing priorities of this page: dependable physical testing first, then coverage of more devices, then the gaps in other families, then delivery.

### Waiting for the owner

1. **`handoff` with a system prompt.** The terminal flow ran once with the owner and the phone on 2026-11-17, for a physical step (rotating it), and the step was confirmed afterwards ([record](verification.md#handoff-with-a-physical-step)). With a passcode set that evening it ran again around re-pairing the phone (Trust and the passcode), and the lock screen was checked: `wake` stops at `awake-locked` without pressing Home, a sleeping phone refuses `tree` and `tap` as `display-off`, and a `tap` on an awake lock screen is dispatched; its receipt now carries `passcodeRequired: true` and a `lockNote`, as the owner chose over refusing it ([record](verification.md#a-passcode-on-the-phone-pairing-handoff-and-the-lock-screen)). An unlock with the passcode, `decline`, `cancel` and a timeout also ran, and an app permission prompt, raised by the probe app's new permission probe and decided by the owner ([record](verification.md#handoff-with-an-app-permission-prompt)). Still unrun: a biometric prompt, and the MCP form flow with a real host, which is also the only way to see the pause on mutations.
2. **Elements with no label and no identifier.** Choosing among elements that share a label is built: `--index` on `press`, `scroll`, `set-value` and `wait` (MCP `index`), decided by the owner on 2026-11-17 after such labels turned up on web pages, and used on the phone to fill a web form ([guide](direct-accessibility.md#current-guarded-native-press), [record](verification.md#web-content-on-the-phone)). Still unreachable: an element with neither label nor identifier, such as the Settings search field, which no selector names; a selector by value or by class would be a separate decision. `--index` has not run on a simulator or through MCP against a device.

### Dependable physical testing

3. **Web content on the phone.** Fixed for reading and pressing on 2026-11-17: the page's tree arrives under the browser's remote element, which the normalizer used to refuse ([guide](direct-accessibility.md#web-content), [record](verification.md#web-content-on-the-phone)). `tree`, `wait`, `press` and typing after a press work on a page in Chrome. Left: the tree is the page alone, so the browser's own controls cannot be acted on by selector while a page holds the display centre, and one combined tree would need the page grafted into the browser's (not built; it changes the process guards of every selector command). `set-value` does not change a web input. The first read after a page load can select the browser instead. `press` refuses an element wider than the display, which a page zoomed by focusing a field produces; whether the guard should accept an element whose centre is on the display is the owner's call. Safari and an in-app `WKWebView` are unchecked.
4. **Recording startup and recovery.** Keyframe requests (PLI/FIR), crash and disconnect recovery are not built. The phone negotiated feedback as `disabled` in the one session where it was read (2026-11-17), so a keyframe request would need a changed offer first; whether the phone accepts one is unknown. Earlier startup failures were traced to the macOS firewall in one case; whether that explains all of them is open.
5. **Release after failure.** The host side is built: after an input with an unknown outcome, or an input owner that exited without releasing, input is refused until `clear-quarantine` ([quarantine](native-input.md#quarantine-after-an-uncertain-release)). On the phone a contact held by a killed process ended by itself, and the quarantine, its clearing and the next tap behaved as on the simulator (2026-11-17). Not built: releasing anything on the device, which that result makes unnecessary for a touch whose sender dies. Still unobserved: a held key or button, and a lost cable or network path mid-input, which reaches quarantine only if the bridge reports an unknown outcome.
6. **Open questions on the phone.** One tap on the Settings search field had no effect while 36 others did; Apple's device services stopped answering once on 2026-11-16 (`mise run diagnose:device-services` captures the evidence before a restart next time). Neither has recurred. An unconfirmed subscription stop did recur on 2026-11-17, three times among about thirty selector commands, after failures and after a successful press alike: each time the socket closed 2 to 3 ms into the stop exchange after one cleanup frame, so the phone closed first; whether that is harmless is not settled. A mode in the touch runner that compares the tree before and after each action, to catch the next missed tap with evidence, is not built. See the [live check plan](live-check-plan.md#questions-still-open).
7. **Unclassified failures.** Errors that are not `CommandFailure` (Foundation, POSIX, decoding and AVFoundation errors) still report `unclassified`; the recording, `frames` and archive sites are classified ([errors](errors.md#unclassified-sites)).

### More devices and more apps

8. **A second iPhone, an iPad, and landscape on a phone.** Everything physical ran on one portrait iPhone 13 mini; rotation and iPad were measured on simulators only. The 200 ms input drain was measured on that phone alone.
9. **`set-value` in other apps.** Run on 2026-11-17 in Settings' Wi‑Fi sheet (a text field and a secure field) and through MCP in the probe app ([verification](verification.md#phone-session-of-2026-11-17)). Three gaps came out of it: a field with neither label nor identifier (the Settings search field) cannot be selected at all (item 2); a secure field reads back as bullets, so `valueMatches` is false although the value arrived; a web input acknowledges the request and keeps its old value (press it and `type` instead). A SwiftUI field with a label or identifier is still untried.
10. **Keyboard layouts on a phone.** Only Spanish – ISO, the layout the test phone uses on its own, has been typed and detected on hardware. A phone's layout cannot be read; `detect-layout` is the substitute. Whether a phone applies the ISO or ANSI table to the 13 layouts where they differ is unchecked.
11. **`frames` beyond portrait.** Rotated displays, other devices, long runs toward the 1000-frame and 1 GiB limits, and a second process competing for the stream.
12. **What apps' recognizers make of three to five contacts.** Delivery is measured; recognition in real apps is not.

### Other families

13. **Real Apple TV, Apple Watch and iPhone Duo hardware.** Everything in [other families](other-families.md) has run on simulators only; on hardware nothing is known.
14. **Apple TV remote touch surface.** Blocked: the simulator's `universalhid` service creates a virtual device but fails to encode its reply (`NSCocoaErrorDomain` 4866), so the device's ID never comes back and no swipe can be addressed ([details](other-families.md#remote-touch-surface-not-built)).
15. **Text entry on Apple Watch.** Keyboard events do not reach watchOS, so `key` and `type` are refused there, and `set-value` changed a SwiftUI field's text without changing the app's bound value ([details](other-families.md#digital-crown-and-side-button-apple-watch)). The remaining route is tapping the text entry sheet's own keys, which is not built.
16. **iPhone Duo gaps.** The Home Screen tree comes back empty on the Duo runtime, folded and unfolded: SpringBoard answers no snapshot at any depth there, so only OCR reads that screen; recheck on the next runtime. On the inner display, four- and five-path `multi-drag` and the centre-hit fallback (for a simulator that reports no frontmost application) have not run, and only one orientation was seen. One `fold` in five was not observed within its 10 s bound on a Mac with three other simulators booted; repeat it alone before changing the bound. `press --label` in two-column layouts is item 2.

### Not built

17. **Simulator `wake` and `paste`.** Both are refused as `unsupported-operation`; `simctl pbcopy` did not reach the simulator's pasteboard, so `set-value` is the Unicode route there.
18. **Physical `logs`.** Refused as `unsupported-operation`. The native `os_trace_relay` route ([research](app-logs-research.md)) is to be built only if `console` proves insufficient. On 2026-11-17 physical `console --os-log` mirrored info and above but not debug-level lines, so debug output from a phone needs that route; whether it is wanted is the owner's call. An output above 64 KiB through `console` is unchecked.
19. **Agent features.** Durable sessions, reusable element handles, automatic prompt detection and notifications, symbolication, `.xcappdata` export, build progress and a build deadline.

### Delivery

20. **Beta release and Homebrew tap.** The release workflow ran once, manually, and failed before the CI fixes; it has not run since. No release has been published and the tap formula has not been tested with a real install ([releasing](releasing.md)).

## Architecture constraints

Device operations communicate with Apple frameworks/APIs from this project's code or Apple executables. Non-Apple device helpers remain blocked. Use maintained general-purpose libraries where useful, and preserve attribution for implementation references.

Keep private interfaces behind backend boundaries. Avoid automatic replay of input or a fallback that changes the operation's semantics. Surface native acceptance, observed effect and cleanup as separate facts.

## Implementation references

Independent protocol references and their licenses are documented in [dependencies.md](dependencies.md). The capability inventory distinguishes those references from this project's implemented routes and live verification.

## Completion criteria

A build or dry run proves planning/compilation, not hardware behavior. Completion requires evidence for the claimed platform, device family, transport and operation, including material failure and interruption cases. A returned receipt alone cannot establish UI effect, exact contact delivery or release.
