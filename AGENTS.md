# Repository instructions

Prefix shell commands with `rtk`. Use `rtk proxy` when unfiltered output is needed.

## Project

- Build `manzanero`, a Swift CLI for Apple-device inspection and control, with optional MCP support sharing the same operations.
- Open-source third-party libraries are permitted. Preserve licenses and attribution. Do not use proprietary device-control binaries as runtime dependencies.
- Keep platform-specific and private interfaces behind backend boundaries. Distinguish implemented features from verified device behavior.

## Commands

Tasks are Bash scripts under `mise/tasks/` (directory namespaces become `group:task`); see `docs/development-tasks.md`.

```sh
mise run build                      # swift build through xcsift; a compiler warning fails it
mise run test                       # all Swift tests through xcsift; a compiler warning fails it
mise run cli -- --help              # run .build/debug/manzanero; does NOT build first
mise run cli tap 0.5 0.5 --device <UDID> --dry-run   # print the planned invocation, touch nothing
mise tasks validate                 # after editing task definitions
```

- The `test` task takes no arguments. Run one suite or test directly, keeping the task's cache path and formatter:
  `swift test --cache-path tmp/swift-cache --filter ToolRunnerTests 2>&1 | xcsift -f toon --warnings`
  (`--filter ToolRunnerTests/nonzeroExitIncludesDiagnostic` for one test). Tests use Swift Testing (`@Test`, `#expect`), not XCTest.
- Hosted runners have about three cores, so the test suite shares a three-thread cooperative pool. Do not spin-wait (`while … { await Task.yield() }`), bound waits with short wall-clock limits, or block a pool thread while another task must make progress; use `TestSignal`, `ManualTestClock` and `.dedicatedThread` from `Tests/ManzaneroTests/TestConcurrency.swift`. Reproduce starvation locally with `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1 mise run test`.
- CI runs exactly `mise tasks validate`, `build`, `check:hardened` and `test`. Run those before committing. `check:hardened` runs the build under the hardened runtime a release is signed with and fails when `doctor` cannot load a private interface; `release:notarize` runs it on the signed binary before it publishes (`docs/releasing.md#the-hardened-runtime`).
- `test:mcp-*` (`test:mcp-live` takes a simulator), `test:media-*`, `test:rsd-*`, `test:native-tunnel`, `test:device-tunnel`, `test:os-trace-relay`, `test:cli-interrupt` and `test:probe-touch` need a real device or a named booted simulator and are opt-in; several send input or record.
- `--dry-run` prints a device command's plan without contacting it; `devices`, `doctor`, `keyboard-layouts`, `ocr` and `mcp` refuse it with exit 64. Read `mise run <task> --help` first and never run one against a device the user has not named.
- `mise run release <version>` is the whole release, each step a mise task: `check:secrets` and `check:identifiers`, the version commit, the tag and one atomic push of `main` and the tag, CI's draft prerelease from `release:ci` (run here when no workflow run comes), then `release:notarize`'s Developer ID signing, notarization and publication on the human owner's Mac (`docs/releasing.md`); a rerun continues where it stopped. Signing and notary credentials never go to CI, and no tap code lives in this repository: the Homebrew tap is another repository. Do not run it or `release:notarize` unless explicitly asked. They and every `git push` are run by the owner from his own terminal: an agent session's shell has no access to the SSH key, so a push from it fails after the local tag has been created.
- The tool needs an Apple silicon Mac, macOS 26.6 or later and Xcode 27 or later, because every device operation goes through Xcode 27, which has no Intel build. `Package.swift` targets macOS 26.6, `doctor`'s `Requirements` entry reports an older Xcode or macOS, and packaging builds one arm64 archive. Do not add an Intel slice, a universal build or an availability check for an older macOS.
- The toolchain must be Swift 6.4+ (the resolved dependency graph requires it) even though the manifest's tools floor is 6.2.

## Architecture

One SwiftPM package, three targets: the `Manzanero` executable, the Objective-C `AppleDeviceBridge` target linked into it, and `ManzaneroTests`. lwIP comes as the `CLwIP` product of the human owner's fork (`https://github.com/kikeenrique/lwip`, branch `swift-package-main`, pinned by tag in `Package.swift`), which adds a package manifest, one configuration and a small C surface (`CLwIP.h`, prefix `ADL`) to lwIP's unchanged sources; the human owner authorized lwIP on 2026-11-19 for the tool's own tunnel and chose the fork over sources in this repository and over a submodule. No lwIP source belongs in this repository: a change to the port is a commit on the fork, a new tag pushed by the human owner, and a new pin here (`swift package edit lwip` to build against a local copy meanwhile). `docs/dependencies.md` is the authoritative description.

- **One parser for both front ends.** The grammar is `manzanero <operation> [operands] (--device <UDID> | --simulator <UUID>)`, defined with Swift Argument Parser in `CLI.swift` (root, shared option groups, target resolution with `MANZANERO_DEVICE`/`MANZANERO_SIMULATOR`) and `CLICommands.swift` (one `ParsableCommand` per operation, with its help). `main.swift` calls `CLI.parse`, never the library's `main()`, and keeps the exit path: usage errors exit 64, other failures 1. `MCPServer.swift`/`MCPTools.swift` (stdio MCP) build a new-grammar argument array per tool and run it through the same parser with `CommandService.run`. An MCP tool is a hand-written schema plus that mapping, so a new operation is a command type plus its execution in `CommandService`, then exposed by both adapters. Generated help is the command reference; give each command an abstract and, where a caveat matters, a discussion.
- **`batch` holds parsed requests, not text.** `BatchCommand` parses every step with `CLI.invocation` when the request is built, so a bad step fails before any runs, and `CommandService` then calls `execute` once per step: a step gets no path of its own. A new operation needs nothing to be usable in a batch. `handoff`, another batch and commands that address no device are refused as steps.
- **`hold <x> <y>` and `release` are batch steps only** (`DigitizerHold.swift`, `docs/gesture-sequences.md#holding-a-contact-across-steps`): a physical device's contact 0 kept down by one live Universal HID stream (`ADCPerformLiveDigitizerReports`, which shares `ADCPerformInput`'s connection, barriers and drain; `ADCRunLiveDigitizer` is its local-sink test boundary) on a thread of its own while the steps between run. `CommandService.runBatch` sends touch steps inside a hold into that stream as contacts 1...4 (`HoldSegment`, built by the same planners) and runs every other step as usual; `BatchCommand` refuses a second hold, a release without one and a five-contact step inside one when the batch is built. A simulator holds the same way since 2026-11-23, on its interface display's Universal HID touchscreen (`ADCSimulatorPerformLiveDigitizerReports`, `HoldTransport.simulator`, `startSimulatorHold`). The lease is held, and the stream released, from `hold` to `release`, the end of the batch, a failed step or a cancellation (`ActiveHold`); an unknown end quarantines the device. Built on 2026-11-22 and run on the iPhone 13 mini the same day: a merged tap, the end of a batch, an interrupt, a failed step, and Control Centre's flashlight and Wi‑Fi pressed by identifier during a hold (`docs/verification.md#hold-and-act-on-the-phone-and-the-apple-tv-without-a-person`).
- **`CommandService.execute` dispatches on a typed `CommandRequest`** (`CommandRequest.swift`). Each command type builds its request in `request(_ target:)`, which is where operands are validated by the operation's own type: `CoreDeviceInput.validated` (in-process physical input and AX), `SimulatorInput` (in-process simulator input and AX), `HandoffCommand`, `ScreenCommand`, `RecordingCommand`, `BuildRunCommand`, `AppDiagnosticsCommand`, and `DeviceOperation`/`DeviceCommand.plan` for the `devicectl`/`simctl` wrappers. The request also says whether a command is read-only (`isReadOnly`), which device the handoff pause sees (`addressed`) and whether it runs under the signal scope (`signalContext`). No code recognises argument arrays below the parser.
- **`coredevice` is the only physical backend for input and AX.** They have no backend option and always run in process. Recording is the one exception: `record --backend devicectl` (the default, which the test phone refuses) or `coredevice`; `frames` uses the same in-process stream as `coredevice` recording.
- **Simulators share the physical code, not a fork of it** (`docs/simulator-input.md`). Input sends the same Indigo dictionaries through the same bridge schedulers over host XPC to the simulator's `dtuhidd` (`AppleSimulatorBridge.m`, `DirectSimulatorInput`). Trees, selector actions and waits run the physical `DirectAccessibilityAction`, `AccessibilitySelector`, `AccessibilityWait` and `DirectPhysicalAccessibility.capture` over the `AccessibilityExchange` protocol, implemented by the DTX `AccessibilitySession` and by `SimulatorAccessibilitySession` (CoreSimulator `sendAccessibilityRequestAsync:`). Per-platform result wording lives in `AccessibilityPlatform`; its physical values must stay the strings physical commands print. `SimulatorEnvironment` injects the simulator lookup, display information and bridge calls for tests. Touch maps the current interface with the simulator's display orientation exactly as physical touch does. Simulator paste and wake are refused. Unicode entry is `set-value` on both platforms (`DirectAccessibilitySetValue` over `AccessibilityValueSetting`).
- **A physical Apple TV** has one external display with no backlight state (`DeviceUIReadiness.isExternal`, `displayPower: external`): the tree selects the frontmost application there, not a centre hit, and takes the display as 1920 points wide. An Apple TV, physical or simulated, is `focusDriven` (`AccessibilityDisplay`): selector actions make no hit test there, because the system process can answer it. `remote` runs on it through `AppleTVRemote.execute` with its own route table (`physicalRoutes`: Menu is Escape and play-pause is Space). The tvOS probe (`Fixtures/ProbeApp/TV/`, scheme `ProbeTV`) reports which remote command an app received. See `docs/other-families.md#a-physical-apple-tv`.

What hides what, measured on 2026-11-24: a layer with `preventsCapture` is black in the device's screenshots and whole in its stream; FairPlay video is black in both while playing, and paused the screenshot keeps the controls while the stream is flat green. Without `--audio` nothing about a recording changes. Two things cost hours on 2026-11-20 and are not faults of the stream: an app can mute its own player when the screen is captured (Apple's TV app does, under Device Hub too), and a sound source that nobody has heard is not a sound source (the probe's first tone started without an error and was silent). Ask whether it was heard before reading silence as a capture fault. The iOS probe plays beeps with `-ProbeTone YES` for this, and since 2026-11-24 the tvOS probe too (`ProbeTVTone`), only with the human owner's word in the Apple TV's room. On that day Apple's Music app, heard playing aloud, gave an Apple TV recording of digital silence: read a player's state before toggling it (a blind `play-pause` started the music instead of pausing it).
- **Both probes take a URL** (`manzanero-probe://…` on iOS, `manzanero-probe-tv://…` on tvOS; `probe.url` and `probe.tv.url` say what arrived), for `open-url`. iOS asks "Open in "Probe"?" the first time, which the tree reads and `press --label Open` answers; tvOS asks nothing.
- **The Apple TV remote's swipes** (`remote swipe-up` and the other three) go to a touch-pad service that the `universalhidservice` creates for the call (`createService`; `ADCSimulatorPerformRemoteTouch` on a simulator, `ADCPerformCancellableRemoteTouch` on a device, where it worked at the first try on 2026-11-20), as the reports multi-touch uses. Launching an app brings both back (the human owner found it with Apple's Home app; the probe's `launch` does the same), so launch the probe and send the steps after it in one `batch`, and count an empty result only when the inputs beside it took effect. The watch returns to the clock two minutes after a launch (Settings › General › Return to Clock). Its `logs` receives nothing until Apple's watchOS logging profile is installed, which is the human owner's step on the iPhone; it lasts three days, and `devicectl device profile remove LoggingProfile` and `reboot` take it off from the Mac (`docs/app-logs.md#an-apple-watch`).
- **Other simulator families** add to the same route rather than fork it: `SimulatorRemote` (Apple TV), `SimulatorCrown` (Apple Watch; on a physical watch since 2026-11-24 `DirectPhysicalCrown` sends the same steps to the watch's own `hid.scroll` service and `PhysicalWatchTyping` taps the keys through physical trees; `type` there is `WatchKeyboard`, taps on the on-screen keyboard's keys, read from the keyboard process named by the app's `AXRemoteElement`, because keyboard events do not reach watchOS; `button side` and `action` reach a physical watch since 2026-11-25 (`ADCPressWatchButton`), and its screen stream is H.264 with its parameter sets in a QuickTime sample description, not HEVC (`MediaVideoAssembler`, `MediaH264Assembler`)), `SimulatorHinge` and `SimulatorDisplays` (iPhone Duo fold, display choice and the interface display that touch, trees and captures follow). See `docs/other-families.md`.
- **Typing in a named layout** builds its tables from the Mac's own keyboard layouts (`KeyboardLayout.swift`; every Text Input Sources and `UCKeyTranslate` call runs under one lock, because concurrent calls crashed); `detect-layout` is `LayoutDetection.swift`. A phone's layout cannot be read.
- **Ownership.** `DeviceLease` takes a per-device advisory file lock for input, AX actions, native recording and `frames`, shared within one process and refused to another. The registry also keeps the quarantine mark: after a touch, button or key input with an unknown outcome, or an input owner that exited without releasing, input is refused as `device-quarantined` until `clear-quarantine` (`DeviceQuarantine`, `docs/native-input.md#quarantine-after-an-uncertain-release`); it is host-side only and sends the device nothing. In MCP, `MCPSessionTransport` holds requests behind `initialize` and `MCPCallOrdering` runs each device's mutations in arrival order (`docs/mcp.md#calls-sent-without-waiting`).
- **`doctor`'s private-interface table** (`Sources/AppleDeviceBridge/AppleInterfaceAvailability.m`) lists every dynamically resolved interface per capability; when an operation's guard changes, update the table and `docs/dependencies.md`. `doctor` also prints a `Requirements` entry (Xcode 27, macOS 26.6, arm64; `Doctor.requirementsEntry`), which is `unavailable` and exits 1 when the selected Xcode or the host is older. `InterfaceTableCoverageTests` fails when the bridge `dlopen`s a framework the table does not list with the same flags, because the table is what the hardened-runtime check loads.
- **Every branch has a `--dry-run` plan** that returns JSON describing the invocation without querying or touching a device. Add one with each new operation; most unit tests assert on these plans and on parsers/encoders rather than on live devices.
- **Process execution goes through `ToolRunner` (synchronous) or `StreamingToolRunner` (async, Swift Subprocess).** Both call `DeviceExecutablePolicy.validate`, which rejects anything outside Apple system binary directories (plus `remotectl`, and `xcsift` for build logs). This is the runtime enforcement of the dependency rule below; do not widen it to make a helper work.
- **In-process native paths** (`DirectPhysical*`, `DirectSimulator*`, `Simulator*`, `Native*`, `Accessibility*`, `Media*`, `RSD*`) implement input scheduling, AX DTX encoding/parsing, RSD discovery, and RTP/HEVC assembly and encoding in Swift. Anything that needs private Apple symbols, sockets or owner lifetimes goes through the C functions declared in `Sources/AppleDeviceBridge/include/AppleDeviceBridge.h` (prefix `ADC`); keep private-interface use behind that header.
- **Cancellation and cleanup are part of the contract.** `CLIInputSignals` turns SIGINT/SIGTERM into cancellation with owned release (exit 130/143); `MCPToolOperations` closes admissions, cancels and drains on EOF with a 30-second forced-exit deadline. A pending handoff pauses non-observation commands for that device via `checkHandoffPause`. Every command that owns something on the device (input, a media stream) must be in `CommandRequest.signalContext`: on 2026-11-21 `record --backend coredevice` was not, and a recording stopped from outside left the Apple TV streaming. Stop a background recording or capture with SIGINT or SIGTERM, never SIGKILL (a task stop may send it). The tool has no stop-all; a leftover stream is ended by a one-frame `frames` run, since the device gives its screen to the newest client.
- **`record` and `frames` share one restart** (`NativeStreamSessions` in `NativeRecording.swift`), and every effect on the device and every clock reading goes through `NativeRecordingLink`; `NativeRecordingLoopTests` drives both loops with scripted RTP sessions and a clock that only the stream and the waits move. Test a recovery change there before a device. Only new video packets count as traffic: a still Apple TV screen repeats one packet a second, and counting it restarted healthy sessions. With `--audio` a restart starts the sound stream again and the sound track a new timeline (`NativeAudioTrack.restart`); after a lost link the stop by identifier names both streams (`ADCStopMediaStreamsByIdentifier`), or the lost sound stream reads as another viewer's session. An interrupt keeps the movie captured so far, and another viewer ends a recording with `stopCause: another-viewer`, both by the human owner's decision of 2026-11-22.
- **Measure sound against picture, do not guess.** The iOS probe with `-ProbeTone YES` flashes white with each round's first beep; compare the round period of the flashes and of the beeps in the movie (a script reading the movie with AVFoundation is enough). That found, on 2026-11-21, a 1.7% drift from floating-point times and a sound stream that ended after 30 s for want of RTCP receiver reports. Times on the movie's timeline are whole numbers; both streams get receiver reports. Ask the human owner before the probe beeps, and check the phone's volume first: it was at its lowest.
- **Handoff has three ways to end** (`HandoffCommand.swift`, `docs/handoff.md`). With `--until` (`HandoffCondition`), `CommandService.watchHandoff` polls the device read-only for `unlocked`, `paired` or a `wait` condition and ends by itself; prefer it, and add a condition there when a new kind of step can be seen on the device. Otherwise a person answers: at a terminal (`TerminalHandoff`), or in an MCP host's form (`MCPHandoffChannel`), which has no fields because hosts add their own Accept and Decline, and whose message is three lines because one host shows no more. Do not add a field or a line to that form without seeing how a host draws it.
- **Selectors are exact by default, with `--index` for ties** (`AccessibilitySelector` in `DirectAccessibilityAction.swift`): by identifier, label or current value (`--id`, `--label`, `--with-value`), or by a tree node's `handle` (`--handle`, `ElementHandle`: the element's pid and accessibility object identifier, the same live element or a refusal, exact, with no `--match` or `--index`; since 2026-11-23) (the kinds and their operation-name suffixes are `AccessibilitySelector.kinds`, so a new kind is added there and not by matching operation names), compared as `--match exact|contains|regex` says (`AccessibilitySelector.MatchMode`, `accepts`; a trailing `--match <mode>` operand before `--index`, for `press`, `scroll`, `set-value` and `wait` only), and the nth distinct match in node order, carried as a trailing `--index <n>` operand and shared by `press`, `scroll`, `set-value`, `wait`, `detect-layout` and `handoff --until` (`detect-layout` refuses `--with-value`, because its probe changes the field's value). `press`, `set-value` and scroll's check afterwards need the target's centre on the display and a hit test that answers the target; the frame may reach past an edge. A plain table row answers the hit by another object than the tree's, which is accepted when it has the target's frame and its identifier, or its label for a target without one (`sameElement`); do not loosen that to the frame alone, because a covering view has the same frame. (`remote sleep` alone also acts in an Apple TV's system UI process, through `overlayProcess`.) `--pid` may name the display-centre process or the process that hosts it (`DirectAccessibilityAction.chooseProcess`), and also a process that one of the foreground application's remote elements shows, with a frame (`AccessibilityPlatform.acceptsShownProcess`): on a simulator by the human owner's word of 2026-11-21 (Safari is the foreground application there and the page is the process it shows), and on a phone or iPad by the human owner's word of 2026-11-25 (an app's web view embedded in native content, whose page is neither the display-centre process nor its host; the probe's `-ProbeWebEmbedded YES`). Not on an Apple TV (`focusDriven`), where `--pid` stays as narrow as before. Nothing else. A hosted process, such as web content inside a browser, answers its snapshot rooted at the host's `AXRemoteElement`; `AccessibilitySnapshot.normalize` accepts that one shape (`docs/direct-accessibility.md#web-content`).
- **Physical input receipts say whether the device was locked.** `CommandService.executePhysical` passes each receipt through `DeviceUIReadiness.annotateInput`, one lock-state query after the input (`passcodeRequired`, `lockNote`). Input is gated on the display being on, not on the lock. A physical screenshot's receipt says the same way whether the display was off (`annotateScreenshot`: `displayPower`, `displayNote`).
- **Errors that are not `CommandFailure`** get a category from their type and domain in `CommandFailure.foreignCode`; add a domain there, not at call sites (`docs/errors.md#unclassified-sites`).
- **Physical `logs` reads the device's log relay** (`OSTraceRelay`, `PhysicalLogCapture`, `docs/app-logs.md#physical-devices`): a lockdown shim service (`RSDDirectoryConnection.shimServicePort`, the bridge's `ADCCopyRSDShimServicePort`) on the tool's own tunnel first, through a relay, and over Apple's tunnel otherwise. It streams one PID, or every process (`Pid: -1`) for a group or `--all`, at every level, and filters on the Mac; the stream is read on a thread of its own so the command service stays free. A one-process capture ends with its process, which the relay does not signal: the tool looks every 2 s, in the relay's `PidList` on the tool's tunnel and in `devicectl`'s process list on Apple's. The relay answers one `PidList` per socket and closes the socket on a second, so each look takes a fresh socket. A directory connection over Apple's tunnel is only good for a few seconds, so open one per stream. Take a PID from a parsed result: on 2026-11-20 a `grep` of neighbouring lines gave the wrong process, and it was sent `terminate`. Built on 2026-11-20 and checked on the iPhone 13 mini the same evening, on both routes.
- **The tool has a tunnel of its own, to a device on its cable or on the network** (`docs/transport.md#a-tunnel-of-the-tools-own`): `ADCOpenDeviceTunnel` (Apple's MobileDevice framework, the Mac's existing trust, the device's CoreDeviceProxy service; always through `usbmuxd`, because the framework's direct connection to a network device is dropped by macOS's Local Network privacy, so do not "simplify" the network branch back to `AMDeviceConnect` on the listed entry), `CLwIP` for TCP over the tunnel's raw IPv6 packets, and `DeviceTunnel` (one queue for every lwIP call, a reader thread, `relay(to:)` on the loopback address so existing address-and-port code runs unchanged with `relayed: true`). On it the tool is the device's only directory peer, so it does not reset the Mac's `remoted`. It is the default since the human owner's word on 2026-11-19 (`MANZANERO_OWN_TUNNEL=0` turns it off): the physical accessibility commands try it first (`DeviceTunnelPool`, which keeps the process's one tunnel between commands; result `serviceDirectory: own-tunnel` and `ownTunnelLink: cable` or `network`) and keep the route over Apple's tunnel as the fallback, saying why in `ownTunnelUnavailable`. Read that field before concluding a run used the tunnel: on 2026-11-19 a whole run fell back silently because the cable was out. A tunnel on the cable ends when the cable is pulled: a `tree` or a wait in flight then runs once more on a new connection (`retriesOnce`, result field `retriedAfter`), and a command that sends input is never run again; do not widen that retry to `press`, `set-value` or `scroll`. A process has one tunnel at a time, and a command starts no pairing by itself. Its private interfaces are `doctor`'s `device-tunnel` entry.
- **An Apple TV gets that tunnel by a pairing of the tool's own** (`docs/transport.md#a-pairing-of-the-tools-own`), since the human owner's word on 2026-11-20: `usbmuxd` never lists an Apple TV, so `manzanero pair` (`PairCommand`) speaks Apple's newer pairing itself (`RemotePairingClient`; SRP in `PairingSRP`, because CryptoKit has none; the PIN from the television) and keeps an identity per device under Application Support (`PairingIdentity`, a private key: never in a repository, a test or a log). `DeviceTunnelPool.openByTrustOrPairing` then falls from the MobileDevice route to `DeviceTunnel(pairedDevice:address:)`: pair-verify and a listener at `_remotepairing._tcp` (port 49152), TLS with the session's key as pre-shared key (`ADCOpenPairedDeviceTunnel`, public Network framework), result `ownTunnelLink: paired`. Three things were learnt the slow way: pair-setup is only accepted by the manual-pairing service, which exists only while the television shows Settings › Remotes and Devices › Remote App and Devices; that service refuses a listener, which the other one gives; and both answer on the device's address in Apple's tunnel, which is where the tool connects, because a command-line tool's connection to a network address can be dropped by Local Network privacy. Each `pair` adds a host named `manzanero` to the device's list: do not pair again to test something that pair-verify can test. `pair` is not an MCP tool and not a batch step.
- **The retired helper backends are gone**, together with their CLI routes, sources, patches and build tasks; git history has them. Do not keep unreachable code as reference. `DeviceExecutablePolicy` still refuses those binaries.
- Temporary process output is written under `./tmp` relative to the current working directory, including by tests.
- **The probe app** (`Fixtures/ProbeApp/`, `docs/probe-app.md`) is the ground truth for touch delivery, log capture and text entry, and raises a real permission prompt on demand (`probe.permission.request`); a watchOS probe (`Fixtures/ProbeApp/Watch/`, scheme `ProbeWatch`, since 2026-11-24) runs watch checks inside an app of the project's own, with a crown readout, a touch pad, a field and thirty rows; launched with `-ProbeList YES` it shows a sixty-row table and a forty-column strip for searches (`probe.list.row.<n>`, `probe.list.col.<n>`), a biometric button (`probe.biometrics.request`) raises a real Face ID or Touch ID prompt, answered on a simulator with `settings --biometrics match|nomatch`; with `-ProbeWeb YES` an app's own `WKWebView` inset 40 points from every edge (`-ProbeWebZoom YES`: a page that zooms into its field), whose page is a process of its own (the display-centre one on a phone, `--pid` from the `AXRemoteElement` on a simulator), and `manzanero-research-phone` is this project's own iPhone simulator for it; `mise run probe-app:test` runs its tests on macOS, and `test:probe-touch` drives its measurement runner.

`docs/verification.md` records what has actually been observed on a device; `docs/feature-status.md`, `docs/roadmap.md` (achieved and pending) and `docs/live-check-plan.md` (hardware runs still owed) summarise it and must agree with each other. `docs/status.md` is the one-table summary of those for the human owner (commands by platform, the routes, what is open): keep it short and plain, and bring it up to date whenever a status in it changes. `docs/device-services.md` lists the services a device offers and which ones the tool uses. Update them rather than implying coverage from a passing build.

## Dependencies

- Device operations must communicate with Apple frameworks/APIs from this project's code or use Apple-provided executables. Do not invoke non-Apple device-control executables.

## Workflow

- Commit each completed task separately with a descriptive message. Verify the change before committing. If Git writes fail, report the error and do not claim a commit exists.
- Keep research, plans, protocol notes, and verification records in `docs/`. Keep the root readme (`readme.md`) as the entry point and maintain its links.
- Put downloads, extracted binaries, temporary tools, caches, and generated investigation artifacts under the visible local `tmp/` directory. Do not use `.tmp/` or `/tmp` for task artifacts. Keep `tmp/` untracked and visible: never commit it, and never add it to `.gitignore` or any other ignore file. It shows as untracked in `git status` on purpose, so stage files by name and never with `git add -A`, `git add .` or `git commit -a`. The first commit ignored `tmp/` and it stayed hidden until 2026-11-18.
- Do not record cleanups (of `tmp/`, build output or caches) in the roadmap, the status pages or any other task list: they are housekeeping, not tasks. The human owner said so on 2026-11-21.
- `tmp/` is disposable, and nothing in it is a record. Never write in a document, a commit message or a report that evidence, logs, screenshots or reports are, were or remain under `tmp/`, and never keep a file there "as evidence". Write what was observed into `docs/` when it is observed; the working files can then be deleted at any time without a word. The human owner said so on 2026-11-18, after a day of sentences such as "Evidence is under `tmp/…`".
- Never commit credentials, local device data, or downloaded commercial app binaries. A device identifier is local device data: in tests and docs use the fixture UDID `00008110-000A11112222801E` or `<UDID>`, never the one a command was just run against. On 2026-11-17 the test phone's UDID was pasted into a test's expected text and pushed; removing it took a history rewrite before the first release.
- Never name a third-party app the human owner had a run made in: not its name, bundle identifier or version, nor an account, profile, title or on-screen text from it, in docs, tests, code comments or commit messages. Write "a third-party streaming app" (or what kind of app it is) and placeholders such as `press --label <profile>`; the observations themselves are what the record needs. Apple's own apps (Settings, Safari, the TV app) and this project's probes may be named. On 2026-11-24 a FairPlay run was recorded with the app's name, profile and series in five commits, and the human owner had to ask twice for it to be taken out.
- After `git add`, read `git status`: paths are matched by exact case, and the readme is `readme.md`. On 2026-11-18 `git add README.md` staged nothing and a commit went out without its readme change.
- A release changes no documentation and needs no step by hand: `mise run release <version>` bumps the version, runs the identifier check and the secrets scan itself and stops at a finding, before a tag makes a later history change expensive. Do not write release results, version numbers of the "current" beta or check results into the docs.
- Record standing instructions and lessons in this file (or a file under `docs/` linked from here when they grow), not in an agent's private memory.

### Delegated agents and git history

- Agents that change the repository work one at a time, directly in the main checkout on `main`. Do not give an agent its own git worktree or side branch, and do not run two writing agents at once; run them one after the other. A read-only research agent that writes only under `tmp/` may run beside one writer.
- Keep `main` a single line: no merge commits.
- Do not rewrite history (rebase, cherry-pick onto a new line, moving a branch) without asking the owner first, even for commits that were never pushed.
- If a stray worktree or branch exists, remove it once its work is on `main`, and say what a git viewer will show until then.
- Why: on 2026-11-16 parallel agent worktrees, a merge commit and a later history rewrite left the day's commits showing twice in the owner's git viewer, as if the work were at risk.

### Stuck Apple device services

- First tell which state it is: `/usr/libexec/remotectl dumpstate` contacts no device, and a connection that has gone stale reads `State: attached` with `No connect() results`. That state is caused by this tool: each accessibility command (`tree`, `wait`, `press`, `scroll`, `set-value`) opens a second connection to the device's service directory, the device resets the one `remoted` holds, and now and then `remoted` never reconnects (`docs/other-families.md#a-physical-apple-tv`). Stop sending as soon as it shows: every command, a failed one too, takes a usage assertion that keeps the stale tunnel alive. On 2026-11-18 a run of retries after a wait that had already ended without clearing kept it stale for another half hour. Input (`remote`, `key`, `button`) still works meanwhile.
- Since 2026-11-20 an Apple TV the tool is paired with (`manzanero pair`) runs its accessibility commands on the tool's own tunnel, where none of what follows happens; it still applies to an Apple TV that is not paired, and whenever a result says `ownTunnelUnavailable`.
- Do not look again for a way to the accessibility service through `remoted` or `CoreDeviceService`. `remoted` connects a client only if it holds the entitlement the device's directory names for the service, and for `…axAuditDaemon.remoteAXService` the device names `AppleInternal`; read from `remoted`'s code and from the directory on 2026-11-18 (`docs/transport.md#the-cost-of-this-route`). The tool's own directory connection is the only route to that service, and the work left is to open it less often. One other route is open and untried: on 2026-11-19 Apple's Accessibility Inspector was seen in `remoted`'s log reaching the Apple TV 4K through the shim `com.apple.accessibility.axAuditDaemon.remoteserver.shim.remote`, which `remoted` gave to MobileDevice's helper (`MDRemoteServiceSupport`), with no reset of the device's connection (`docs/verification.md#accessibility-inspector-on-the-apple-tv`). This tool opens it too, through the MobileDevice framework (`ADCOpenAccessibilityShim`, `AccessibilityShim`; opt-in checks only, no command). What answers there is the Inspector's audit server (`XADAuditServer`), which refuses this tool's tree requests (`clientNeedsAccessibility:`, `processDataFromHost:`) and has its own (`deviceElement:valueForAttribute:` and 42 others, `docs/verification.md#the-accessibility-shim-opened-by-this-tool`): do not point the existing `AccessibilitySession` at it, build on its own requests. Never send that server a request whose argument form is a guess: on 2026-11-20 `deviceElement:valueForAttribute:` with the attribute's name as a plain string made the Apple TV's `axauditd` abort, twice (`docs/verification.md#an-element-read-through-the-shim`). Read the form from Apple's AccessibilityAudit framework first: it loads on the Mac, and its `AXAuditObjectTransportManager` (`sharedManager`, `transportDictionaryForObject:`) writes any of its objects as it goes on the wire, with nothing sent to a device; that gave the attribute's form, with which requests succeed. Run a new request once, then check `last-crash --process axauditd` before running it again (it reads the top directory only, and the device moves reports into `Retired` within the hour: after a long run also read `reports list Retired`), and check the device is awake before reading an empty answer as a fact. How Apple's own client writes each request is in the Inspector's `AccessibilityAuditDeviceManager.framework` (`XDMDeviceTransportBased`, readable with `otool -tV`), and the names the device serves are in the tvOS simulator runtime's `axauditd`. What the route can do was measured on 2026-11-20 (`docs/verification.md#the-inspectors-cursor-the-whole-hierarchy-and-a-press-through-the-shim`): a press by the Inspector's cursor, with no reset and the focus unmoved; no tree (values only under the cursor, no frame, no focus, lists skipped or scrolled), no `set-value`. Do not start a tree on it again without a new fact. `press` on a physical Apple TV is built on it since 2026-11-20 (`InspectorPress`, `InspectorRoute`; `MANZANERO_INSPECTOR_PRESS=0` turns it off). The order of a press there, by the human owner's word on 2026-11-20 (`InspectorRoute.pressInOrder`): the tool's own tunnel (paired), then the Inspector's cursor. Since the human owner's decision of 2026-11-21 an Apple TV's accessibility commands never go over Apple's tunnel: with neither route a press is refused, and `tree`, `wait`, `scroll` and `set-value` are refused when the tool's own tunnel is unavailable (`DirectPhysicalAccessibility.appleTVTunnelRefusal`), because that route left the Mac's connection stale again that day. Do not bring it back; an iPhone keeps it as its fallback. Each route passes to the next only while nothing has been pressed, and says why in `ownTunnelUnavailable` or `inspectorUnavailable`. Keep that rule: a failure of a press itself (the Activate request, or an action on the tunnel) is an unknown outcome, never a reason to press again by another route.
- Read the current notes of the reference projects listed in `docs/dependencies.md` before a long investigation of a transport question. On 2026-11-18 one of them had already recorded, in one sentence, that `createservicesocket` is refused for the accessibility service, and it was rediscovered over an hour before anyone looked. `gh api repos/<owner>/<repo>/contents/<path> -H 'Accept: application/vnd.github.raw'` reads one file.
- A device's service directory is read once per tunnel (`AccessibilityServicePorts`: memory within a process, `~/Library/Application Support/manzanero/service-ports.json` across processes) and an accessibility command refuses to start on a connection that is already stale (`StaleDeviceConnection.refuseIfStale`). Keep both when changing `DirectPhysicalAccessibility`: each directory connection makes the device reset the Mac's `remoted`. For a run of accessibility commands on a device, prefer one `batch` or one MCP session, or keep separate commands close together: the tunnel, and with it the saved port, is replaced some seconds after the last command.
- Read the Mac's log with `/usr/bin/log`, never plain `log`: in zsh `log` is a builtin, the call fails ("too many arguments"), and with stderr discarded an empty result looks like "nothing was logged". On 2026-11-20 a "no interruption" was reported from exactly that. And read `remoted`'s lines for one device (`coredevice-<n>>`, from `remotectl dumpstate`): other devices on the network log interruptions and handshakes every half minute.
- When a private Apple daemon refuses something, read its log and then its code before trying variations: `log show` gave the sentence ("Client lacks privilege to interact with service"), `xcrun otool -tV` on the daemon gave the test behind it, and Hopper gave the library's side. Four rounds of guessed requests came before that and decided nothing.
- Read what the docs already say before repeating an experiment: that same night an identity of the tool's own in the directory handshake was tried as a fix, when `docs/other-families.md` already recorded that it had not helped on the phone.

- When every query to a connected device times out, read the logs before restarting `CoreDeviceService` or `remotepairingd`: a wide `log show` (or `log stream`) window for both and a `sample` of each process. `mise run diagnose:device-services` collects them. Write what they show into `docs/verification.md` before anything else, then ask before restarting them. On 2026-11-16 a restart fixed such a hang but nothing had been read, so the cause is unknown. On 2026-11-18 one device (an Apple TV) timed out alone after a run from Xcode ended, while the phone answered: the log showed `remotepairingd`'s `RSD Heartbeat … failed after 0ms` for that device every 30 seconds, and a restart of both services, with the owner's word, fixed it. Look for that line first. It happened three times that day; `remoted`'s own log (`log show --predicate 'process == "remoted"'`) shows "Device connection interrupted" with no "Handshake complete" after it (`docs/other-families.md#a-physical-apple-tv`).

## Implementation and validation

- Use Swift 6.2 or later and preserve strict concurrency checking.
- Invoke external tools with argument arrays, without shell interpolation of user input. Keep CLI stdout suitable for the documented machine-readable format and diagnostics on stderr.
- Run applicable build checks through `xcsift`; use meaningful tests for protocol encoding, parsing, and process behavior.
- Check installed tool help or authoritative sources before relying on Apple tool flags or private protocol details.
- Record OS/tool versions and limitations for device integration checks. A successful build or dry run does not prove live-device functionality.
- An Apple TV's video needs an offer without VideoToolbox's resolution adaptation (`VRAE` in the feature list Apple's negotiator offers for HEVC): with it the device changes the picture's size between key frames and every standard decoder, ffmpeg's included, shows the pictures on top of each other. `NativeMediaFrames(plainOffer:)` takes it out for an external display (`ADCOfferVideoWithoutResolutionAdaptation`), and recording and `frames` work there since 2026-11-20 (`docs/verification.md#the-apple-tvs-video-fixed-an-offer-without-resolution-adaptation`). Two days went to wrong causes first (a blank stream, a missing audio stream): keep the stream (`MANZANERO_KEEP_STREAM=1`), decode it with a second decoder on the Mac, and read the negotiated feature lists before blaming the packets.
- Compare a decoded frame with a screenshot of a bright, moving screen before calling a stream blank or wrong. On 2026-11-18 the Apple TV's stream was recorded as blank from one run on a dark, still screen; two days later it turned out to be the screen, right for its first frames, in the corner of a larger frame (`docs/verification.md#the-apple-tvs-video-stream-read-packet-by-packet`), and a task had been planned on the wrong cause.
- Look before you say what a device shows. Take a screenshot or a tree before telling the owner that something is on the screen, and again after an action; on 2026-11-17 a prompt was reported as "should now be on the phone" without a look, and the owner had to ask for the check.
- A coordinate that a later step depends on must come from a look at that screen, in the same command where possible, and a failure must be read for what it says before it is reported as an effect. On 2026-11-22 a `gesture` built from an earlier screenshot tapped Control Centre twice where Wi‑Fi had been: the first tap opened Music, and the second failure was reported as the Wi‑Fi cut although Wi‑Fi was still on, until the human owner said so. Control Centre's page follows the opening swipe's length (a swipe from the top edge to 0.15 of the height opens page 1; to half the screen it moves on to page 2), and `tree` times out while Control Centre is in front: close it before reading the app. Opening Control Centre cancels the app's touches.
- Observing an Apple TV is not free of effect. On 2026-11-18 a pass of `readiness`, `apps`, `media-status`, `screenshot` and `screen ocr` on a sleeping Apple TV switched it on, and the television connected to it; which command did it is unknown. Tell the owner before the first command to an Apple TV, and say that the television may come on.
- The room the Apple TV is in stays quiet. Never play audio there and never send a volume key; the human owner said so on 2026-11-20, after a run had started the device's system audio stream toward the Mac. The stream itself is allowed since the human owner's word later that day: for implementing sound in recordings, and whenever a command asks for it (`record --audio`). It captures what the device plays and plays nothing. Starting playback there (an app, a song) still needs the human owner's word each time. For a video check, put the tvOS probe in front first: its screen is still and silent, where an idle Apple TV goes to a moving screen saver.
- The Apple TV 4K may be used again, since the human owner's word later on 2026-11-20, with the room kept quiet as above. An Apple TV asleep for hours answers slowly: a first `remote home` was refused before any input ("HID service did not become ready") and a screenshot timed out, while the Mac's log showed its heartbeats answered after up to 34 seconds; a second `remote home` some minutes later woke it. Read the heartbeat times (`mise run diagnose:device-services`) before treating that as a fault.
- A device session covers the device and the apps the owner named. Ask before opening a third-party website, another of the owner's apps, or changing a setting; on 2026-11-17 a browser and two public sites were used without asking.
- An MCP host keeps running the server binary it started. After a rebuild, have the owner reconnect the server before testing a change through the host.
